# Emulsion: independent deep review

**Reviewer stance:** adversarial principal review covering color science, film lab, iOS/Metal and product. Read-only: no repo files and no Linear data were changed.
**Date:** 2026-10-28 · **Repo:** `emulsion` @ `b560b6a` (note: `docs/RESEARCH.md` is **untracked** in git: `git status` shows `?? docs/RESEARCH.md`, yet the Linear document calls it the "source of truth").
**Linear:** project P-MOV-1 "Emulsion". I read all 74 issues (MOV-5…MOV-78), the 5 milestones and the document "Engine research report (fact-checked)". The document is identical to `docs/RESEARCH.md`.
**Scratch artefacts:** all experiments live in `…/scratchpad/` (`probe/` is a Swift package that depends on EmulsionCore by path, `py/model.py` is a Python mirror of FilmModel, and `pdf/` holds the datasheet chart extractions).

---

## 1. Executive verdict: **ADJUST (strongly), and rethink the positioning**

- The engine is cleanly built. All 20 tests pass (I re-ran them). The GPU kernel matches its Swift mirror, NaN/Inf/huge inputs never produce non-finite output, and every log curve constant I checked is correct. The scaffolding is better than most first versions.
- **But the plan is aimed at the wrong risk.** It spends M2 on a spectral model while three things are unvalidated or broken:
  1. **The market premise is factually wrong.** Dehancer shipped a rebuilt native iOS 26 app for iPhone and iPad with camera log profiles and video editing (2026). A free spectral film simulator (spektrafilm) now ships in darktable, in vkdt and as a Resolve OFX plugin. "Physically modeled" is no longer a moat.
  2. **The input side has real correctness gaps.** The RAW path very likely clips highlight headroom (`extendedDynamicRangeAmount = 0`). Video legal/full range isn't handled (errors of ±1 stop). Apple Log 2 / Apple Wide Gamut (iPhone 17 Pro) is missing. JPEG/HEIC inversion posterizes highlights.
  3. **The performance targets are unproven and likely unrealistic** with the current per-pixel graph.
- **Recommendation:**
  1. Fix inputs, then bake the color path to a LUT.
  2. Ship a thin stills vertical slice to real users.
  3. Run colorist and consumer interviews **before** the spectral model.
  4. Re-scope the spectral model as one candidate, judged against a cheap "camera-RGB→film-layer fit" baseline and ideally against real film test data.

  - spektrafilm (the renamed agx-emulsion) is now a darktable processing module (https://docs.darktable.org/usermanual/development/en/module-reference/processing-modules/spektrafilm/), a vkdt module (https://jo.dreggn.org/vkdt/src/pipe/modules/filmsim/readme.html) and, per its README, has a Resolve OFX port. ### F-2 · CRITICAL (verify immediately) · The RAW developer probably discards highlight headroom and lets Apple gamut-map
- **Evidence:**
  - `Developer.swift` sets `raw.extendedDynamicRangeAmount = 0`.
  - The SDK header (`CIRAWFilter.h`, macOS 27 SDK) says: "Allows the output to have an Extended Dynamic Range with values greater than 1 possible. A value of 0 indicates no extended dynamic range output."
  - `gamutMappingEnabled` ("The default value is true") is never turned off.
  - With `boostAmount = 0`, scene 1.0 is only about +2.5 stops over 0.18. The film model's shoulder spans +2…+8 stops (my mirror: +4 stops → 0.891, +6 → 0.974 display-linear).
  - The "materialized negative keeps headroom" test uses a synthetic wedge, not CIRAWFilter output, so nothing tests this.
- **Impact:** if the output is clipped at 1.0, the product's headline benefit (film latitude on RAW highlights) silently disappears on real photos, and halation never triggers from RAW (threshold 2.0 > 1.0).
- **UNVERIFIED:** I found no DNG on this machine to measure. The header semantics are quoted exactly.
- **Fix:**
  - Set `extendedDynamicRangeAmount = 2` and `isGamutMappingEnabled = false`, and decide on `highlightRecoveryEnabled` (iOS 26).
  - Add a fixture test asserting `max(output) > 1` on a real ProRAW and Bayer DNG with clipped sky.
  - Document `baselineExposure` handling.
- **Linear:** MOV-10 (expand), MOV-8 (fixture must contain overexposed RAW).

### F-3 · HIGH · Video legal/full range isn't modeled; S-Log3/LogC3/V-Log and HLG need opposite conventions
- **Evidence:**
  - The S-Log3 formula is defined on code values / 1023 of a legal-range signal. colour-science `log_decoding_SLog3(..., in_normalised_code_value=True)` applies `full_to_legal` when data is *not* normalised code values (https://colour.readthedocs.io/en/master/_modules/colour/models/rgb/transfer_functions/sony.html). Sony's summary says 18% grey is code 420 and data is "limited from 64 to 940".
  - HLG (BT.2100) expects E′ after narrow-range expansion.
  - `Developer.scene(fromEncoded:as:)` has a single path with no range parameter. The kernel tests feed exact float code values, so they cannot catch this.
  - MOV-39 says only "CIImage colorSpace nil". YCbCr→RGB conversion of a `420v`/`x420` buffer still applies range expansion and the matrix (UNVERIFIED exactly which, per CI version).
- **My computation** (`python3` in the log, §3 E8). If a narrow-range file is range-expanded before an S-Log3/LogC3 decode:

  | Code value | Error |
  | --- | --- |
  | CV 200 | −0.88 stops |
  | CV 420 (grey) | −0.06 stops |
  | CV 600 | +0.33 stops |
  | CV 800 | +0.76 stops |
  | CV 940 | **+1.05 stops** |

  The reverse mistake on HLG gives −0.64 stops at CV 940.
- **Impact:** every pro-log clip is graded with distorted contrast. This is the classic bug the owner asked about, and it is present by omission.
- **Fix:**
  - Add a per-input `signalRange` (legal/full) and a YCbCr matrix policy.
  - Read `kCVImageBufferYCbCrMatrixKey` and the video-range pixel format, and decode YCbCr yourself (or verify CI's behavior) in a dedicated kernel.
  - Build real 10-bit HEVC and ProRes fixtures with known code values for both ranges.
- **Linear:** MOV-39, MOV-42, MOV-48, plus a new issue (see §6).

### F-4 · HIGH · Apple Log 2 / Apple Wide Gamut (iPhone 17 Pro) is unsupported and absent from the backlog
- **Evidence:**
  - Several sources report that Apple Log 2 keeps the Apple Log curve but uses a new wider gamut, and that Apple published an Apple Log 2 white paper (Sept 2025). Examples: CineD JP (https://www.cined.com/jp/?p=432738), gamut.io (https://gamut.io/apple-log-vs-apple-log-2-whats-actually-different/), RedShark on Kino 1.4 (https://www.redsharknews.com/kino-1-4-apple-log-2-support).
  - `ColorSpaces.swift` maps `.appleLog` to Rec.2020 primaries only.
  - **UNVERIFIED:** the exact Apple Wide Gamut primaries. The white paper must be read from developer.apple.com.
- **Impact:** on the target hardware (iPhone 17 Pro / Duo), the default log footage would be decoded in the wrong gamut, giving systematic hue and saturation errors.
- **Fix:** a new input case with the primaries taken from Apple's PDF; metadata detection (MOV-42); tests.
- **Linear:** new issue; MOV-42.

### F-5 · HIGH · Display-referred (JPEG/HEIC) inversion posterizes highlights, shifts saturated colors, and feeds halation unbounded "scene" values
- **Evidence** (GPU, my probe E3/E4):
  - **Top codes span a huge scene range.** P3 code 252 → +5.97 stops, 253 → +6.58, 254 → +7.77, 255 → **+12.00 (737.3, the bisection ceiling at `displayToScene` hi = 12)**.
  - **Lowering exposure exposes the spacing.** At exposure −3, codes 252/253/254/255 re-render at 227.8/237.9/248.0/254.5, i.e. about 10-code jumps per input code (banding in skies).
  - **Shadows crush.** Codes 1–3 all collapse to −16 stops.
  - **Saturated colors shift at zero edits.** P3 (0, 0.6, 1) goes from OKLab L 0.666 → 0.439, chroma ×1.37, hue Δ 21.5°. P3 (0.9, 0.3, 0.2) goes L 0.643 → 0.601.
  - **The round-trip test hides this.** `testDisplayPhotoTonesSurviveTheRoundTrip` checks only steps 4…59 of 64 and only lightness, so it excludes exactly these regions.
- **Cause:** per-channel inversion of the *neutral* curve (`displayToScene` uses `.y` of a gray render), followed by a forward pass that adds crosstalk, dye mixing and gamut mapping. The forward neutral curve tops out at about 0.998 (my mirror: +12 stops → 0.99824), so encoded ≥ 254.8 is unreachable and pins to the ceiling.
- **Impact:** JPEG/HEIC is probably the most common input for the "easy" app, and skies are the most common highlight.
- **Fix:**
  - Clamp the inverse at a soft scene ceiling (e.g. +6 stops with a smooth knee) and dither.
  - Prefer the gain-map HDR path (MOV-49) whenever present.
  - Consider inverting with chroma preservation (invert luminance, keep display chromaticity, scaled) rather than per-channel.
  - Extend the test to the full code range and to chroma.
- **Linear:** new issue; MOV-49.

### F-6 · HIGH · MOV-5 ("re-fit print to 2383, quick win") will over-contrast the look; its acceptance criteria are internally inconsistent
- **Evidence:**
  - My digitization of the native 490×496 chart image (§3 E9) confirms the report's numbers: 2383 midscale slope (D 0.5→3.5) B 3.46 / G 3.25 / R 3.69; peak about 4.0–4.7; Dmax 4.10.
  - Our print curve: peak 2.55 (G), Dmax 3.36.
  - **But simulating the naive refit** in my Python mirror (same negative, recalibrated) gives:

    | Print model | Display gamma at mid-gray | Contrast ratio |
    | --- | --- | --- |
    | Current | 1.24 | 997:1 |
    | 2383-like peak 4.15 | 1.81 | 6,973:1 |
    | 2383-like peak 4.62 | 2.02 | 7,970:1 |

  - Gamma at +2 stops falls to 0.39–0.44.
  - The datasheet slope is Status A print density vs log exposure from **tungsten + heat glass + Series 1700 filter**. To be paired with it, the negative must be expressed in **printing density** (not the 250D Status M curves, whose straight-line gamma I digitized at R 0.47, G 0.56, B 0.55). A projected print is also seen through flare.
  - Kodak LAD prints mid-grey to a 1.0 visual neutral (Status A 1.09/1.06/1.03): "the LAD patch is printed to a neutral gray of 1.0 visual density" (H-61b; 250D datasheet). Relative to Dmin about 0.05, that is about 0.11 of open-gate. The engine puts mid-grey at 0.17. This is a deliberate display choice that should be documented, not a bug.
  - **Acceptance-criteria conflict:** MOV-5 demands a fit "within 0.05 density". MOV-16 tolerates ±2% of axis range (±0.12 density on 2383's 6.0 axis). The source raster is 64 px per density unit with 2–3 px lines, so 0.05 ≈ 3 px is about the noise floor.
- **Impact:** the "cheap, noticeable" quick win will likely make images harsh, and the existing tests can't catch it (they test neutrality, not tone).
- **Fix:** reframe MOV-5 as "end-to-end tone reproduction target":
  - Fit print and negative together in printing density.
  - Add a flare term.
  - Set the acceptance criteria on the system curve: mid-grey display gamma within a target band, black and highlight anchors, and colorist A/B.
- **Linear:** MOV-5 (reword, downgrade from Urgent to High), MOV-16, MOV-26.

### F-7 · HIGH · Grain seeds are broken for integers: every integer seed gives (almost) the same grain
- **Evidence:**
  - `hash()` computes `fract(p.xyx*k + seed)`. Adding an integer before `fract` is a no-op.
  - Probe E7 (512×256, grain = 1):

    | Comparison | Mean \|Δ\| |
    | --- | --- |
    | Seed 1 vs 2 | **0.017 codes** |
    | Seed 1 vs 3 | 0.077 codes |
    | Seed 1 vs 1.5 | 2.16 codes (independent) |

  - The default `Adjustments.seed = 0`, so every photo also gets the same pattern.
- **Impact:** "new pattern per frame, seeded" (MOV-43) with integer frame numbers would produce **frozen grain** (a "dirty screen" effect). Every photo shares a pattern.
- **Fix:**
  - Hash the seed into the lattice coordinates (e.g. PCG/xxhash on `(i, j, seed)` as integers).
  - Add a test that seeds n and n+1 are uncorrelated (|ρ| < 0.05).
  - Derive the per-photo seed from the asset ID.
- **Linear:** new bug; MOV-43; MOV-30.

### F-8 · HIGH (legal) · The 2023 grain paper's method is patented
- **Evidence:** US 12,705,810 B2, "Real time film grain rendering and parameter estimation":
  - Applicant/assignee Northwestern University; inventors Tian, Wang, Zhang, Pappas.
  - Filed Mar 18 2024 (provisional Mar 16 2023), **granted Aug 11 2026**.
  - The abstract claims synthesizing grain "as correlated signal dependent noise" from derived second-order statistics.
  - Source: https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12705810 (page 1 read).
  - The paper is Zhang, Wang, Tian, Pappas, ACM TOG 42(4), 2023 (SIGGRAPH archive https://history.siggraph.org/?p=132288).
- **Impact:** MOV-21 proposes evaluating it as a "runtime method". Implementing it commercially may need a license. The research report says nothing about patents at all.
- **Fix:** add patent checks (freedom to operate) to MOV-14's license audit. Treat 10.1145/3592127 as reference-only unless licensed. Get counsel's view on Newson (no patent found; UNVERIFIED) and on AV1 grain outside an AV1 codec.
- **Linear:** MOV-21, MOV-14, MOV-30.

### F-10 · HIGH · Performance targets are unproven and very likely unrealistic for the current graph
- **Evidence:**
  - My `swift test -c release --filter PerformanceProbe` on an **Apple M4 Max with a 32-core GPU** (`system_profiler`):

    | Size | Full grade | Look only |
    | --- | --- | --- |
    | 1600×1200 | 5.8 ms | 2.7 ms |
    | 4032×3024 | 20.0 ms | 6.9 ms |
    | 8064×6048 | 94.7 ms | 35.4 ms |

  - The report never names the Mac.
  - Per pixel, `filmSystem` runs two `filmRender` calls, a 16-iteration OKLab bisection (`fitP3`, each step a cube plus 2 matrices) and the transcendental chain. Halation adds 2 blurs and local tone a 4-level pyramid plus an edge-preserving upsample.
  - **Rough estimate (UNVERIFIED):** scaling by GPU core count (A19 Pro has 6) gives about 30 ms for a 1600 px full preview and about 75 ms for a 4K frame. That compares with targets of 8.3 ms (MOV-12, 120 Hz) and 33 ms including decode and display (MOV-40, 4K30).
  - spektrafilm's own README: "roughly 10 seconds to process 6 MP images" (Python, CPU), which supports baking rather than evaluating spectrally at runtime.
- **Fix:**
  - Bake the per-pixel color path (input → film → gamut/output) into a 33³/65³ LUT with a log shaper **now**, for the parametric model too, not just after spectral.
  - Rebake on printer-light, saturation or exposure changes (about 36k evaluations, sub-ms on GPU). Keep exposure as a pre-LUT log offset.
  - During interaction, run halation at reduced resolution.
  - Set device-specific p95 frame-time budgets.
  - MOV-38 "kernel fusion ≥ 30%": Core Image already concatenates color kernels (Apple WWDC guidance; verify with `CI_PRINT_TREE`), so measure first.
- **Linear:** MOV-11, MOV-12, MOV-24 (pull forward), MOV-38, MOV-40, MOV-52.

### F-11 · MEDIUM-HIGH · Wide-gamut inputs (Rec.2020 / AWG / S-Gamut3) are hard-clipped per channel inside the film model
- **Evidence:**
  - `filmRender` does `max(sensitivity·p, 1e-7)` per channel.
  - Probe E2 (HLG Rec.2020 primaries, neutral render), hue shift in vs out:

    | Primary | At 0.18 | At 0.72 |
    | --- | --- | --- |
    | Blue | **20.4°** | **17.9°** |
    | Yellow | 10.2° | 10.2° |
    | Green | 6.7° | 5.8° |
    | Cyan | 5.5° | 9.0° |

  - Apple Log and iPhone HLG are Rec.2020, so this is the *main* video path, not an edge case.
- **Fix:**
  - Promote MOV-50 (input gamut compression) to High and move it to M1.
  - Apply ACES RGC-style compression in the input→working step (the CC BY 4.0 spec is already cited in the kernel).
  - Or move the film's working space to a wide one (e.g. AP1/Rec.2020) and gamut-map only at output.
- **Linear:** MOV-50.

### F-12 · MEDIUM · Halation is driven by luminance, not red-layer exposure
- **Evidence:**
  - `halationSource` uses `lumaSRGB`.
  - Probe E6: a pure P3 red and a pure P3 blue source of equal luminance produce **identical** glow, Δ (47.97, 20.52, 8.30) codes at 14 px.
  - Physically, the light that reaches and reflects off the base is mostly red (blue is absorbed by upper layers and the yellow filter), so blue sources should halate far less.
  - Minor: a source at the frame edge gets +4% glow, because the replicated border feeds the blur via `clampedToExtent`.
- **Fix:**
  - Drive halation from red-layer (and a little green-layer) exposure, i.e. `sensitivity` row 0.
  - Inject it into the layer exposures inside the film model rather than as RGB scene light.
  - Use mirrored or zero padding at edges.
- **Linear:** MOV-32.

### F-13 · MEDIUM · Grain preview/export "matching" fails beyond ±15%, and the test tolerance hides it
- **Evidence** (probe E5, mid-grey, grain = 1). Ratio of preview σ to Lanczos-downsampled export σ:

  | Preview long edge | Ratio |
  | --- | --- |
  | 1179 px (iPhone screen) | 0.73 |
  | 1600 px | 0.77–0.79 |
  | 2556 px | 1.14–1.18 |

  The ratios are consistent across 3024/4032/8064 exports. The test `testPreviewAndExportCarryMatchingGrain` allows ±35%. Grain *size* also differs: the cell is clamped to ≥ 1 preview px, i.e. 1/1600 of the frame versus 1/2400 at export.
- **Smaller defects:**
  - "Zero-mean" holds in cube-root lightness only. Linear-light mean bias is +0.93%, and +0.65 code after downsampling.
- **Fix:**
  - Render preview grain by a statistically correct model: band-limited noise with an analytically known PSD, filtered to the display's sampling rate.
  - Tighten the test to ±10% σ plus a PSD comparison.
  - Define the grain unit as a fraction of the frame at every scale.
- **Linear:** MOV-30, MOV-43.

### F-14 · MEDIUM · The film model and plan omit negative dye cross-absorption and masking couplers; datasheet curves alone won't give the look
- **Evidence:**
  - In `FilmModel.system`, negative density goes straight into print exposure per channel. There are no negative dye unwanted absorptions, no orange mask, and no printing-density conversion. The print has a `printDyes` matrix; the negative has none.
  - spektrafilm's README (from someone who has done this): "data-sheet curves are really not enough to reproduce a decent film look… masking couplers… are very important for achieving the desired saturation."
  - The 250D dye chart is "D-mins subtracted" and peak-normalized (datasheet page 4), so the mask must be reconstructed.
  - The research report never mentions masking couplers. Its F5 conflates them with DIR couplers.
- **Fix:** add a "negative dye set + masking + printing density" step (and its research note) before the print refit. Standard references are Giorgianni & Madden and Hunt.
- **Linear:** MOV-17, MOV-18, MOV-26, MOV-27; research F5/F9.

### F-15 · MEDIUM · Productization gaps missing from the backlog
- **Evidence:**
  - **Privacy manifest:** `Emulsion/Model/AppSettings.swift:17` uses `UserDefaults`, a required-reason API, and there is no `PrivacyInfo.xcprivacy` in the repo (`find` returned nothing). App Store submissions need it (https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api).
  - **Export metadata:** `Renderer.export` strips **all** metadata, not just GPS. Capture date, camera EXIF and orientation are dropped, so exported photos land at the wrong place in Photos timelines.
  - **Preview path:** previews go through `cgImage(...format: .RGBA8)`, an 8-bit SDR CGImage (`RenderService.swift:34`). There is no EDR or 10-bit preview, so preview and export can't match for HEIC 10-bit or HDR.
  - **Kernel binaries:** the checked-in metallib is reproducible. I rebuilt the macOS metallib and got an identical SHA-1, `a84241f8…`. CI can therefore enforce staleness, but MOV-13 doesn't say so.
  - **Linear hygiene:** none of the 74 issues has blocking relations, an estimate or an assignee (checked MOV-5, MOV-23, MOV-40 with `includeRelations`). Dependencies live only in prose.
- **Fix:** new issues (see §6).

### Also noted (Low)
- **NaN and Inf.** A NaN or Inf in any channel turns the pixel black (the NaN propagates through `Y` into all channels and is then caught by `max(·, 1e-7)`). This is safe, but it is a visible black speck. There are no non-finite outputs anywhere, including the full graph with halation and local tone.
- **Negative toe.** The negative toe is broader than 250D. At −6 stops the model keeps about 50% of mid-grey gamma, while the datasheet is nearly flat (about 15%). Logistic symmetry can't do both a long straight line and a short toe; use a toe/shoulder spline or a Richards curve on the negative too.
- **Chromatic adaptation.** ACEScct uses Bradford for D60→D65; ACES 1.x ODTs use CAT02. The difference is below 0.001 and is a documentation item only.
- **Warmth and Tint range.** Each runs ±2 printer points (`FilmLook.printerPoint = 0.05`), i.e. 1/6 stop of printing light at full slider. That is very subtle compared with a lab's typical ±12-point range. This is a UX choice; document it.
- **Local tone order.** Local tone runs after the film, on display-referred values, and can push values above 1 when brightening highlights (they clip later). Consider moving it to log scene space before the film.

## 4. Alternatives analysis

### Spectral and color approaches

| Approach | Pros | Cons | Recommendation |
|---|---|---|---|
| **Jakob–Hanika 2019** (sigmoid-polynomial) | Smooth, bounded reflectances. BSD-3 reference code exists (`mitsuba-renderer/rgb2spec`, GitHub API), so no clean-room needed. Tables for wide gamuts | Reflectance-bounded, so emissive/HDR values need scaling. Near the spectral locus (Rec.2020/AWG primaries) spectra become very narrow, which makes film-sensitivity integration unstable | Good candidate for the *offline* bake. Use the BSD code with notice |
| **Mallett–Yuksel 2019** | Trivial and fast | **Valid only inside sRGB**. The spektrafilm thread notes it "transforms and clips the values to sRGB before the spectral upsampling" (pixls.us). Unusable for P3/Rec.2020 log without clipping | Reject for wide-gamut inputs. The report omits this limitation |
| **"hanatos2025"-style observer-exact upsampling** (used in spektrafilm/vkdt) | Zero error for the CIE observer | Forum reports say wide tails over-saturate with film sensitivities that extend into UV/IR, and skin is problematic. No paper (**UNVERIFIED**) | Watch; don't depend on it |
| **Measured-reflectance basis** (PCA of Munsell, Otsu, skin, forest sets; vkdt lists these sets) | Spectra are *natural*, which is right for metamerism on real surfaces | Doesn't cover lights/neon; needs a gamut fallback | Use as the **training set** for fitting, not as the runtime upsampler |
| **Direct camera-RGB→film-layer-exposure fit** (least squares or root-polynomial, Finlayson 2015, over training spectra × illuminants, through the datasheet sensitivities) | Exposure-invariant (root-polynomial); works for any input gamut; no upsampling artefacts; cheap; this is what ACES IDT derivation (rawtoaces) does | Loses metameric detail beyond the training set | **Build this first as the baseline**, and require the full spectral model to beat it in a blind colorist test (MOV-23) |
| **Empirical measured film** (Yedlin) | Ground truth including scan/print/projection. Yedlin: color response "can be treated as a 3D transformation"; "Scattered data interpolation can map one data set precisely onto the other" (https://www.yedlin.net/NerdyFilmTechStuff/OnColorScience/) | Costs film stock, processing and scanning (**cost UNVERIFIED**); needs a lab | Commission one small test (ColorChecker SG, skin, neon; 250D/500T; ECN-2; 2383 print or scan) as the **validation oracle** for whatever model ships |
| **Cineon / printing-density approach** (SMPTE RP 180, ADX/APD) | Standardized printing-density responsivities, the right frame for neg→print | The standards are paywalled (SMPTE/ISO 5-3) | Use RP 180 (already cited) as the printing-density definition; derive the Status A/M digitization corrections from it |
| **spektrafilm / darktable / vkdt** | Most complete open model; proves the concept | GPL-3 code; CC BY-SA profiles; the author claims "inspired by its methods" counts as derivative | Do not use or study the code. Consider contacting the author |

### Display rendering

| Approach | Pros | Cons | Recommendation |
|---|---|---|---|
| darktable filmic/sigmoid, AgX, **OpenDRT** | Mature display transforms | darktable and OpenDRT are GPL-3 (GitHub API); AgX repos have no license file | Ideas only. The print simulation *is* the DRT |
| **ACES 2.0** | Hue-stable chroma/gamut compression; HDR family; Academy license; OCIO 2.4.2 removed the "Preview" label | Not a film look; JMh is heavy per pixel | Borrow the gamut-compression design for output; offer an ACES 2.0 interop mode in Pro (Filmbox Pro already offers ACES 2.0/1.3/RCM, so we're behind there) |

### Grain

| Approach | Pros | Cons | Recommendation |
|---|---|---|---|
| **Newson 2017** (Boolean model) | Physically grounded; resolution-free | Slow; B&W silver model, not dye clouds per layer; IPOL code GPL-3.0-or-later (IPOL page) | Offline reference only, implemented from the paper |
| **Zhang et al. 2023** | Fast; parameter estimation | **Patented (US 12,705,810 B2)** | Do not implement without a license |
| **AV1 film grain** (AR + piecewise scaling) | Efficient for video | Exporting grain parameters needs an AV1 encoder; as far as I know iOS VideoToolbox doesn't expose AV1 *encode* (**UNVERIFIED**). AOM patent licence scope outside codecs is **UNVERIFIED** | Drop the "AV1 grain export" sub-goal for iOS. HEVC exports with grain will balloon in bitrate or be smeared; test that instead |
| **Yedlin empirical** (match the amplitude distribution and PSD of scanned grain) | Simple; matches what viewers perceive | Needs real scans | Best practical target for grain v2: band-limited noise with measured PSD, scaled per layer density |
| **Current value noise** | Cheap | Seed bug; preview/export mismatch | Replace |

### Architecture

| Approach | Pros | Cons | Recommendation |
|---|---|---|---|
| **Core Image** (current) | RAW integration; tiling; auto kernel concatenation; EDR destinations; small code | Opaque scheduling; limited control of intermediates; CIColorKernel only | **Keep for v1** |
| **Custom Metal compute** | Shared memory for blurs and grain; precise control | More code; must re-solve tiling and memory | Only for grain or halation if profiling shows a bottleneck |
| **OCIO at runtime** | Standard configs; ACES 2 | C++ deps on iOS; binary size; doesn't plug into CI kernels directly | **Offline only:** CI reference values, LUT export validation |
| **LUT bake point** | — | — | Bake input→(scene ops)→film→gamut→output into one LUT per input/output pair with a log shaper. Keep halation (scene, pre-film), local tone and grain as spatial passes. Rebake on slider change. The same LUT drives preview, export and `.cube` export, which removes three parity problems at once |

4. **Is open-sourcing the engine** (or collaborating with spektrafilm's author) acceptable? It would turn a licensing risk into community goodwill.
5. **Which devices are in scope?** The minimum device sets the performance budgets: iPhone 15 Pro (first Apple Log) vs 17 Pro / Duo only.
6. **Is iPhone HLG a "scene" input,** or should the app steer video users to Apple Log / Apple Log 2?
7. **Naming:** are you prepared to ship without Kodak/Fuji names (descriptive names only) if counsel says so?
8. **Pricing model:** one-time (like Chromagraph) or subscription (like Dehancer)? It changes the scope of v1.
