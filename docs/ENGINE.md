# Emulsion engine

Emulsion is a film lab for colorists. It takes camera RAW, log and HDR video, and ordinary JPEG/HEIC/MP4. RAW and log are decoded into **scene light**; HLG is decoded as nominal scene light; ordinary JPEG/HEIC only gets an estimate of scene light, because the phone's rendering can't be undone, and is printed relative to itself (see [Input contracts](#input-contracts)). The result is printed through a modeled photochemical system. The look comes from a negative → print chain behaving like one. It is not a stack of filters or a LUT.

The UI should stay simple, while the engine underneath is something a colorist can trust: it's measured, its stages are documented, and the GPU output is verified against a reference model.

## Architecture

Every photo renders through one process, `Adjustments.process`: the film process below (the default) or a non-film process that shares the input side and the controls (see [Non-film looks: Digicam 2004](#non-film-looks-digicam-2004)). `Renderer.render` dispatches on it.

```
source ──▶ input transform ──▶ scene light (linear, 0.18 = mid-gray) ──┬──────────────▶ film system ──▶ local tone ──▶ output
          RAW develop         one working space for every source       │                exposure, Color               P3 today;
          log / HLG curves                                             └─▶ halation ──▶ layer exposure + glow         Rec.709 2.4,
          display estimate                                                 glow (blur)  negative + grain              PQ/HLG next
                                                                                        → print (printer lights)
```

| Stage | File | What it does |
| --- | --- | --- |
| RAW develop | `Developer.swift` | Apple `CIRAWFilter` with Apple's rendering switched off: no boost, local tone map, extra contrast, extended dynamic range, gamut mapping or shadow bias. Gamut mapping was what capped highlights near 1.0, so turning it off keeps their headroom and lets out-of-gamut colours stay negative for the film model. Highlight recovery stays on, so clipped channels are estimated and blown highlights stay neutral. The result is demosaiced, white-balanced, linear scene light scaled by the file's BaselineExposure (MOV-79) and then by one per-file exposure anchor (MOV-134, see [Exposure anchor](#exposure-anchor)). White balance is applied here, in the camera's colour space, by `CIRAWFilter` (`neutralTemperature`/`neutralTint`): as shot unless `Adjustments.whiteBalance` sets a temperature and tint (MOV-10, see [RAW white balance](#raw-white-balance)). It is separate from the printer-light Warmth and Tint, which act at print. ImageIO types many ProRAW files read from memory as plain TIFF, so files are identified, and handed to `CIRAWFilter`, with a DNG type hint |
| Input transforms | `ColorSpaces.swift`, `VideoSignal.swift`, `inputTransform` / `ycbcrInputTransform` kernels | Apple Log, S-Log3/S-Gamut3.Cine, ARRI LogC3/LogC4, V-Log, DaVinci Intermediate/DWG, ACEScct (Bradford from ACES white), HLG (BT.2408 scaling), Rec.709 and Display P3 display encodings. Code values become the BT.2100 signal E′ using the declared range (legal or full); 10-bit Y′CbCr frames use their tagged matrix (BT.709 or BT.2020). S-Log3, LogC3 and V-Log formulas take 10-bit legal-range code values, the rest take E′ |
| Display-referred sources | `FilmModel+Display.swift`, `displayToScene` and `filmSystemRelative` kernels | JPEG/HEIC/Rec.709/Display P3 get a scene estimate through the film's own neutral print response, with soft ends so display white and black land on a finite ceiling (+4 stops) and floor (−9 stops). At render time the change the film predicts for the user's edits is applied to the photo itself, so zero edits reproduce it and edits act like the film would on that estimate. It is a re-render, not a recovery of the scene (see Input contracts) |
| Film system | `FilmModel.swift`, `filmSystem` kernel | Layer sensitivities (crosstalk) → negative H&D curves → printer lights → print H&D curves (Richards toe) → print dye cross-absorption → 10^−density relative to paper white. Mid-gray is calibrated neutral, like a timing lab |
| Highlight chroma retention | same | The one non-physical step. Bright saturated light (neon) blends toward a ratio-preserving render above +1.5 stops, so it doesn't band. Midtones are unaffected; timed (warm/cool) neutrals above +1.5 stops lose part of their timing, and very bright saturated colors stay tinted instead of reaching white (artistic choice under review) |
| Halation | `Halation.swift` (`Kernels.halationGlow`), `halationSource` and `halationMix` kernels, inside `filmSystem` / `filmSystemRelative` | Light reflected at the back of the base re-exposes the red layer (a tenth as much the green, an artistic estimate; never the blue). The glow is the layer exposure (after the Color control's saturation, before the exposure control) blurred by a 3-Gaussian fit of the derived single-bounce profile, scaled by base thickness over an assumed 35 mm frame, at reduced scale over mirrored edges (narrow blurs with exact taps); the film kernels add it to each layer's exposure after exposure and saturation, so Color does not re-tint it and it commutes with the exposure control (linear, no threshold). Uniform areas are unchanged, so it shows only at edges and points; highlight chroma retention sees the light with the glow's change of exposure. Backing: none, undercoat or rem-jet (default; both backings estimated at 5% of the unbacked return). On a photo it enters the edited print only (FILM-THEORY §6.1) |
| Local tone | `LocalTone.swift` | Halo-free Highlights/Shadows: a box-averaged base layer with edge-preserving upsampling (carried over from the GradingCore study; the current test allows ≤3 codes of halo) |
| Grain | `Grain.swift`, `grainNoise` kernel, inside `filmSystem` / `filmSystemRelative` | Random negative density per layer, added before printing, so the print shapes it. σ per layer is the datasheet's granularity (H-1-5207, 48 µm aperture) at that layer's exposure, scaled to the pixel by Selwyn's law on the assumed 24.89 mm frame; the noise is white per pixel, so previews and exports carry the same grain per film area. Amount 1 is the datasheet's granularity; below 1 is an artistic reduction. The print's own grain is not modelled (FILM-THEORY §6.2) |
| Interactive speed | `Renderer.materialize` | The developed preview is rendered once into a half-float buffer, so slider moves never re-run the RAW develop or the JPEG inversion |

## Input contracts

Not every input can tell us what the scene looked like. Each source has a contract: what its decoded values mean, and what the engine may say about them. In code the contract is `InputContract`, declared by each input on `InputColorSpace.contract` and carried by every developed image on `Negative.contract`.

| Source | Contract | What the engine does | What it may claim |
| --- | --- | --- | --- |
| RAW (Bayer DNG, ProRAW) | Scene-referred | Apple `CIRAWFilter` with Apple's look switched off | Linear scene light from Apple's develop. ProRAW is already computational photography, so "scene light" means Apple's linear develop, not a sensor measurement. Highlight headroom is MOV-79. Overall exposure follows the file's DNG profile through the exposure anchor (MOV-134), an estimate, not a metered level |
| Camera log (Apple Log, S-Log3, LogC3/LogC4, V-Log, DaVinci Intermediate, ACEScct) and linear P3 | Scene-referred | The manufacturer's published curve and gamut matrix | Scene light; the decode is verified against colour-science references |
| HLG (Rec.2100) | Nominal scene | BT.2100 inverse OETF with BT.2408 scaling | Decoded as scene light by the standard, but phone HLG is rendered by the camera before encoding, so it is not claimed to be the scene |
| JPEG, HEIC, Rec.709, Display P3 | Display-referred | Scene estimate from the neutral print response (soft ends at the top and bottom), then printed relative to the photo | A re-render of the photo, not the scene. Zero edits reproduce it: gray codes 0–255 within 1 code (measured 0.06), a real 8-bit JPEG of mild chroma within 0.25 codes of its own decode (measured 0.07). For colors near the P3 boundary the output gamut fit lowers chroma, to 94% at the primaries (OKLab ΔE×100 up to 2.1; on a saturated gradient a low channel rose by up to 10 codes); lightness and hue are kept. Display white is estimated at +4 stops, black at −9 stops; the ceiling, the floor and the two knees (display-linear 0.75 and 0.006) are engineering choices, not measurements. Limits: edits act on an estimate; the Color control acts more weakly on extremely saturated source colors; 8-bit sources still quantize; HDR headroom is discarded (MOV-49); halation is driven by the estimate, so a clipped white glows like a +4-stop light (peak glow source 0.72, computed from the halation source at the estimate; the earlier unbounded inverse gave about 4) |
| Camera viewfinder frames (the camera's processed video) | Preview estimate | `Developer.viewfinderNegative(from:)`: the display-referred scene estimate, approximated by a 1D curve sampled once from the Swift mirror (built-in `CIColorCurves`, 1024 steps in extended Display P3 encoding) and the inverse layer sensitivity (`CIColorMatrix`), with no per-pixel solve; then printed absolutely, like the RAW capture it previews | A preview of the RAW render made from the camera's processed video frame, never scene light. Its print is within OKLab ΔE×100 0.04 of printing the exact estimate (`ViewfinderEstimateTests`). How far it is from the captured photo (Apple's video tone mapping, white balance, noise reduction, clipping) is unmeasured until device testing (MOV-121). Preview only: never exported or stored. Known gap in the digicam process: a viewfinder frame has no as-shot white balance, so the viewfinder shows the 5500 K reference cast while the captured RAW gets the as-shot residual (strongly orange under tungsten; see [Non-film looks](#non-film-looks-digicam-2004)) |
| HDR stills (gain-map HEIC/JPEG, PQ/HLG HEIF) | Display-referred | Read as their SDR rendition (the gain map is ignored; PQ/HLG are tone-mapped by Core Image), then as above | Same as display-referred; HDR headroom is discarded until MOV-49 |

### Exposure anchor

Bypassing Apple's rendering also drops two hints in the file's DNG profile: the ProfileGainTableMap (what `CIRAWFilter` calls local tone mapping) and the ProfileToneCurve (its boost). 12 MP ProRAW puts its brightening in BaselineExposure, which the develop keeps; 48 MP ProRAW puts 2–3 stops of it in the gain table, so without the anchor 48 MP files developed 2.0–2.9 stops darker (median) than Apple's own render.

The exposure anchor (`ExposureAnchor.swift`, reported as `Negative.exposureAnchorStops`) is one scalar per file, applied as a single linear multiply, so ratios between pixels, values above 1.0 and negative components are untouched. It is computed only when Apple can apply a gain table for the file (`CIRAWFilter.isLocalToneMapSupported`). Deliberately excluded, with anchor 0: a DNG with a tone curve but no gain table, and non-DNG RAW, where Apple's boost is its own look curve rather than the file's DNG profile (unverified on such files: no sample exists). Derivation: the filter renders a 256 px thumbnail twice, once with the develop's linear settings and once with the gain table and tone curve applied (`localToneMapAmount` and `boostAmount` at 1; on real files these match the DNG SDK's gain table within 0.025 stops and the tone curve within 0.02 stops at mid-gray). The anchor is log2 of the geometric mean of the luminance ratio (profile ÷ linear) over the pixels the profile renders within ±1 stop of 0.18; with under 1 % of pixels in that window every pixel counts; it is clamped to −2…+5 stops (measured −0.56…+2.95). The thumbnail size is fixed, so previews and exports get the same anchor (equal within 1e-6 at 1024 and 512 px on 25 files).

What it is: an estimate that places the tones the file's own profile renders at mid-gray at scene 0.18. It is not a measurement of scene reflectance. Its limits:
- The pixel selection depends on the scene: the window picks whichever pixels the profile renders near mid-gray, and the gain table changes per shot. On 25 files the anchored median lands within 0.58 stops of Apple's default render (mean absolute 0.17; files ≥ 40 MP and < 20 MP differ from it by −0.02 stops on average, where 48 MP used to sit 2–3 stops lower); for the 22 iPhone 15 Pro Max files the residual log2(anchored ÷ Apple) spans −0.28…+0.58 stops, so two shots from the same camera can be placed differently by up to about 0.85 stops relative to Apple's render.
- The profile render uses `boostShadowAmount` 1, its neutral value; Apple's default (0.9 on all 25 files) darkens shadows below about 0.12 on top of the tone curve. It has no effect on the linear develop (pixel-identical, synthetic and real files).
- The absolute level is unverified until a grey card is shot: no file in the sample set has one.
- Cost, Mac only, develop + materialize of a 1024 px preview (median ms without → with the anchor; iOS device timing, and the target phone's files, are untested): iPhone 15 Pro Max 48 MP 942 → 971, iPhone 15 Pro Max 12 MP 111 → 125, iPhone 14 Pro 48 MP 1145 → 1996, iPhone 12 Pro 12 MP 94 → 155, Pixel 8 Pro Bayer 125 → 187. It depends on the file generation and on what the process decoded before: Apple sometimes reuses a filter's RAW decode between renders and sometimes decodes again for every render (seen on the iPhone 14 Pro, iPhone 12 Pro and Pixel files when another file was developed first; developed alone, the same three cost 965, 114 and 185 ms with the anchor). The two thumbnails go through a context that caches intermediates (shared with `Renderer.materialize` and `export`, MOV-147), so the second reuses the first's decode in every case; the output render can still pay one more decode, which no render order avoided. Full tables are in the MOV-134 PR. So the app measures it once per file: `RenderService` remembers the anchor of a file's first develop for the session and passes it back (`develop(_:maxDimension:whiteBalance:exposureAnchorStops:)`) for other preview sizes, white balances and the export, which then skip the thumbnails and cost the same as a develop without the anchor (Mac, 1024 px, median ms: iPhone 14 Pro 48 MP 1141 given vs 1145 without and 2002 measuring; iPhone 12 Pro 98 vs 96 and 155; Pixel 8 Pro 130 vs 125 and 177).

### RAW white balance

`CameraWhiteBalance` (temperature in kelvin, tint) replaces the file's as-shot white balance when a RAW file is developed (MOV-10). `CIRAWFilter` turns it into a camera neutral and white-balances in camera space, before the camera matrix, which is what a white balance at develop means; a printer-light correction after the develop cannot do this. Values are clamped to Apple's documented ranges (2000–50000 K, tint −150…150). `nil` is as shot. `Negative.asShotWhiteBalance` is what the decoder reads from the file whatever the develop was set to, for a UI to start from; it is nil for photos that aren't RAW, and `RenderService` then never develops them again for a white balance. A recipe neither stores nor changes it: it describes the light one photo was shot under. The digicam process reads it for its residual auto-white-balance cast (see [Non-film looks](#non-film-looks-digicam-2004)), so that cast follows the light the photo was shot under, not the develop's white balance.

- Order: the exposure anchor is measured at the as-shot white balance, then the new white balance is set, then the output is rendered, so the anchor does not move when the white balance does (identical on synthetic and 25 real files). Setting it after the anchor does not make `CIRAWFilter` decode the file again (the output render takes about the same time with and without a change), setting it before or after the preview scale gives identical pixels, and a develop costs the same with and without a white balance. Timings are in the MOV-10 PR.
- Previews: `RenderService` keeps one developed preview per photo and size together with the white balance it was developed at; a new white balance replaces it. For a photo that isn't open in an editor that means developing the file again (reusing its exposure anchor, measured as shot, so the same at any white balance): about 1 s for a 48 MP ProRAW at 1024 px on a Mac.
- Interactive white balance (MOV-137): the photo open in an editor (`EditSession` tells `RenderService.open`) keeps its `RAWDecoder`, Apple's `CIRAWFilter` held alive with the file's bytes, and each new white balance is one more `negative(whiteBalance:)` of it: the file is neither read nor decoded again, and the anchor is the one measured when the decoder was made. `Developer.develop` is itself one `negative` of a decoder, so a kept decoder and a develop from the file give the same pixels at every white balance (tested pixel-equal on synthetic Bayer and linear DNGs, preview and full size). As shot is the untouched filter: a decoder never sets a neutral until a white balance asks for one, because setting a neutral to its own value is not bit-identical to leaving it alone. Back at as shot after another white balance, it sets the as-shot temperature and tint again and develops within 1e-6 of the untouched file (measured 6.0e-7 linear, 9.5e-7 Bayer; tolerance 2e-6), checked against a `CIRAWFilter` nothing has set a neutral on. One decoder is kept, in draft mode (the anchor is measured on a separate decoder first: measuring leaves draft mode off, and a kept full-quality decoder rendered each step 3–4 times slower), at the largest preview size asked for; smaller previews of the open photo are resized from it. It is released when the editor closes, another photo opens, the photo is forgotten or it is exported (so the export's full-size decode isn't held beside it; the next preview makes it again). The export still develops from the file at full size with the same white balance and anchor. Measured on a Mac only, on synthetic uncompressed 12 MP DNGs at a 1600 px preview, on a machine busy with other work (so the spread is wide): a white balance drag went from 7–22 to 49–149 rendered updates per second (best runs 22 → 63 Bayer, 22 → 149 linear), and a Warmth drag is unchanged within noise (best 505 before, 479 after; its code path is the same cached preview). The MOV-10 probe measured a kept-alive filter at 27–33 ms per step on a real 48 MP ProRAW and 7–12 ms on 12 MP, against 970 and 126 ms from the file. Unverified: device timing and memory, real ProRAW files in this path, and the iPhone 12 Pro / 14 Pro / Bayer files on which Apple sometimes decodes again between renders (MOV-134). Draft mode changes nothing on the synthetic DNGs, so the kept draft decoder's first preview is tested equal to a non-draft develop only there; on real files it may differ within the draft tolerance. An as-shot white balance outside Apple's documented range would show the rulers at the clamped value (no such file seen). Only one photo is open at a time: a second Mac editor window takes the decoder, and the first reads its file for each white balance step until it reappears (the Mac app has one editing window, `Apps/macOS/AGENTS.md`).
- Editor controls: RAW photos get a White Balance group with Temperature and Tint rulers that rest at the as-shot values (read from the file without developing it). Temperature moves in equal mired steps (10⁶ / kelvin; 5 mired per tick, about 150 K at 5500 K and 20 K at 2000 K), which are roughly equal visible steps, and shows kelvin rounded to 10 K; Tint is in Apple's units, 2 per tick. Back within a tenth of a tick of as shot on both rulers the white balance is `nil` again, so the photo is unedited and develops exactly as shot. The scale and step sizes are design choices, not measurements.
- Apple's tint is the light's distance from the Planckian locus × 3000 (Duv in CIE 1960 uv; positive is a green light, corrected towards magenta), the DNG SDK's scale: a file tagged with D65 reads 6502 K, tint 9.77, against 6504 K and 9.52 for D65's Duv. Measured, not documented by Apple.
- Limits: the synthetic chromatic patches are lit by scaling camera channels (von Kries in camera space), not a spectral simulation, so the chromatic checks test the mechanism, not how a real sensor sees colour under tungsten. The 22 iPhone 15 Pro Max samples are Lightroom re-saves, so on them only the mechanism is tested.

**RAW decoder 9 is not used.** `CIRAWFilter.decoderVersion` stays at the file's default, which is "8.dng"/"8" on all 25 real DNGs and on the synthetic ones: decoder 9 is opt-in (WWDC26 session 305, "What's new in Core Image RAW"; the SDK header's "newest available" does not match what the filter reports). On the same files decoder 9 changes the image a lot: the iPhone 14 Pro 48 MP file's mean RGB goes from (0.1485, 0.1724, 0.1883) to (0.0248, 0.0202, 0.0118), medians move both ways from file to file, and synthetic Bayer neutrals develop with a warm tint (R/G 1.04–1.22). Apple DTS forum thread 843445 reports colour problems with it too. Until it develops neutrals neutral and keeps the exposure, the develop stays on the default decoder (measured on macOS 27.2, MOV-10).

**Every render goes through a caching context (MOV-147).** Apple's RAW decode at full size with `contrastAmount` 0 (which the develop sets) returns corrupted tiles, such as magenta/red blocks or shifted copies of the image, when the rendering `CIContext` doesn't cache intermediates. Intermediate caching is Core Image's default (`CIContext.h`); the engine had turned it off for every render. It was reproduced with `CIRAWFilter` alone, without Emulsion's kernels, and confirmed by an independent review (macOS 27.2, M4 Max):
- On a 48 MP iPhone 15 Pro Max file, the first render in a process was clean and 7 of the next 8 were corrupt, even on one context and one thread. Every process gave the same sequence of outputs, so it depends on the decoder's state from earlier renders, not on timing or memory pressure (peak memory varied from 1.4 to 3.2 GB with the same results).
- On a 12 MP file, the first render after another context had decoded the same file was corrupted.
- Each of these rendered the same every time: every other bypass setting on its own; contrast at 0.01, 0.1 (Apple's default) or 0.5; a half-scale decode; and a caching context, whether fresh, shared, or cleared after every render.
- `insertingIntermediate(cache: true)` didn't help, and `clearCaches()` alone was unreliable.
- Synthetic DNGs (12 and 48 MP, linear and Bayer) never triggered it.

So every render (`cgImage`, `materialize`, `export`) and the developer's exposure anchor share one `CIContext` that caches intermediates; each render clears its caches afterwards. The one exception is viewfinder frames:
- `Renderer.viewfinderImage` renders through a context without caching, and it accepts only a camera frame's preview estimate (`.previewEstimate`, made only by `Developer.viewfinderNegative`). It throws for anything else, so a RAW develop can't reach that context.
- The exception keeps the 30 fps path as fast as before: on the caching context a 1600 px frame took about 0.8 ms more (Mac).
- CI checks both rules: `everyRenderCachesIntermediates` and `viewfinderRendersOnlyCameraFrames`.

Code that renders a develop through a context of its own, such as a test harness or a tool, must cache intermediates too.
- History: the first fix (#59) guarded only `materialize` and `export`, which left `cgImage` of an unmaterialized full-size develop exposed (the app always materializes first, but tools and new paths may not). The real-file test, with a full-size `cgImage` check added, failed on that code in 2 of 3 runs (9 mismatches each) and passes with one context.
- Repeatability: now repeatable on four real files (`FullSizeRenderTests`, opt-in): exports, materialized negatives and full-size `cgImage`, 8 repeats each.
- Output: within one 8-bit code of the old path's uncorrupted render (half-float rounding).
- Cost (Mac):
  - 48 MP export: peak resident memory about 0.2–0.5 GB higher (one half-float full-size intermediate is 390 MB), with no change in time.
    - Peak physical footprint, which counts GPU buffers (resident memory may not): with Apple's decoder alone, a full-size 48 MP render takes 2.00 GB uncached and 2.43 GB cached.
    - Through the engine, a full-size develop + render + JPEG export peaks at 2.2–2.3 GB (48 MP), 3.1–3.3 GB (50 MP Bayer) and 1.7 GB (12 MP), at 1.0–1.2 s, 0.19–0.23 s and 0.13–0.16 s.
  - Rejected alternative: buffering every RAW develop in `Developer` would keep a lazy decode out of every negative. But a float buffer raised the 48 MP export peak to 5.6–5.9 GB (50 MP: 6.8–7.4 GB). A half-float buffer cost only +0.2 GB, but changed 0.009 % of output values by up to 14 codes against today's render.
  - 1024 px preview develop + materialize (median of 12, three alternations): 12 MP 115–151 → 141–145 ms, 50 MP Bayer 160–194 → 175–229 ms, 48 MP unchanged (1187–1382 → 1215–1236 ms). That's once per photo, size or white balance, not per slider move.
  - Editor previews on the caching context:
    - `PerformanceProbe`, 1600 px: full look 3.8–4.3 → 6.1–7.6 ms; look only unchanged at 3.0–3.7 ms.
    - Slider drags (`SliderDragProbe`, synthetic 12 MP, 1600 px; ranges over 2 runs before and 3 after; noisy): Warmth drag, Bayer 219–362 → 181–246 and linear 351–366 → 317–530 updates/s; white balance drag, Bayer 72–77 → 66–75 and linear 151–156 → 124–153 updates/s.
  - Viewfinder frames: unchanged (1600 px 2.7–2.9 → 2.6–3.0 ms; 12 MP 7.0–8.6 → 6.7–6.9 ms).
- Concurrency: a thread clearing the caches every 2 ms during ten 48 MP exports left all of them identical (two runs), so a `clearCaches()` doesn't disturb a render already in flight.
- Unmeasured on device, including peak memory.

**Sub-black policy.** Decoding keeps sub-black signals (legal-range footroom, compression undershoot) as negative light; clipping is the film model's job. Where a specification defines values below its range, the engine follows it: Apple Log holds at R₀, and the log curves' toes and sRGB's linear segment extend linearly. Where it doesn't (BT.2100 HLG, BT.1886 gamma 2.4), the curve is extended oddly (mirrored), so every decode stays monotonic through black. colour-science mirrors HLG the same way; for BT.1886, which colour-science clamps, the reference generator applies the engine's convention.

## Stock files

A stock's parameters live in a JSON stock file, not in code. `FilmStock` (`FilmStock.swift`) is the file format; `FilmModel(stock:)` turns it into the immutable model the renderer and kernels use.

- **Format** (`formatVersion` 1): `name`; `provenance` (`source`, `notes`, and optional `fitDate`, `tool`, `sourceSHA256`, `fitResiduals`, omitted when absent); `negative` (`sensitivity` 3×3, `gamma`, `densityRange`, `exposureOffset`); `print` (`gamma`, `minimumDensity`, `densityRange`, `shape`, `dyes` 3×3); `rendering` (`highlightChromaRetention`, `middleGrayOut`). Matrices are three rows of three, row-major. Gammas are density per log10 exposure; offsets are log10 exposure relative to mid-gray. `encoded()` writes sorted keys, so a stock always encodes to the same bytes.
- **Validation** (`EmulsionError.invalidStock` with the reason): unknown `formatVersion`, wrong array lengths or missing keys; non-finite numbers; gammas, density ranges or print shape ≤ 0; negative minimum density; `middleGrayOut` outside (0, 1); `highlightChromaRetention` outside [0, 1]; sensitivity or dye rows not summing to 1 (±1e-6; that is what keeps neutrals neutral); and a print the printer lights can't time, meaning mid-gray misses `middleGrayOut` by more than 1e-6. `errorDescription` is the plain localized sentence; the reason is `failureReason`.
- **Default:** `Resources/Stocks/emulsion-default.json`, hand-tuned and not fitted to any datasheet, loaded once as `FilmLook.stock`. A test pins its render bit-for-bit to the engine before stock files existed.

## Digitized stock data

The offline `EmulsionFit` target (never linked into an app, not a library product) holds a manifest per digitized stock in `Sources/EmulsionFit/Resources/StockData/<stock>/`, naming the PDF (with its SHA-256), page, conditions, axis calibration, the per-point reading error and the SHA-256 of each traced CSV, plus the fitted stock files (see "Fitting stocks"). The traced curve CSVs are not in the repository (`docs/DECISIONS.md`, 12 Nov 2026): anyone with the public PDF can re-trace them with `Tools/stock-digitizing/digitize.py`. They are local reference data, read from `EMULSION_REFERENCE_DATA` or else `~/Documents/Emulsion Research/datasheet-tracings`; the loader refuses any CSV whose digest differs from its manifest. Where that folder is missing, only the manifest checks run. `docs/STOCK-DATA.md` ("Digitized curves") covers the method, the error estimates and the cross-check.

- **Manifest checks on load:** the manifest's `stock` must match its directory, and grid steps, pixel scales, uncertainties, x ranges, spans and the camera-stop anchor must be finite and in range, or loading fails naming the field.
- **Audit:** samples sit on the manifest's grid and inside each curve's traced extent, and characteristic curves never fall by more than one chart pixel of density.
- **Dye-sum check** (MOV-17): the yellow, magenta and cyan dye spectra, with non-negative least-squares scales, against the sheet's neutral; target max |residual| ≤ 0.05 D. Dye densities are used as drawn, negative lobes included (the negatives' magenta dye dips below zero near 445 nm). Negatives: the acceptance compares neutral − minimum density, because the dye curves are drawn "D-mins subtracted" while the neutral and minimum-density spectra are drawn as measured; the unsubtracted comparison is reported as a diagnostic. Print film: the acceptance compares the visual neutral over 400–700 nm, where the three image dyes account for it; the full overlap and the scales-fixed-to-1 residual (with its mean) are diagnostics. With scales fixed to 1 the neutral sits above the plain dye sum by a roughly flat amount over 400–700 nm and rises steeply below 400 nm; the chart does not say what the extra density is.

## Fitting stocks

`emulsion-fit` (target `EmulsionFit`, offline only, never linked into an app) fits stock parameters to the digitized datasheet charts described above. It reads the manifests (bundled, or `--manifests <dir>`) and the traced curves from the reference data (`--data <dir>`, else `EMULSION_REFERENCE_DATA`, else the default folder); `check` and `negative` stop with an error when there is none.

- **Committed fits:** `StockData/<stock>/negative-fit.stock.json` for 250D and 500T, written by `emulsion-fit negative --stock <id> --out <dir> --fit-date 2026-11-12` (default base and name). They hold parameters, provenance (including the characteristic CSV's SHA-256) and residual statistics only; the fit report and plot table contain traced samples and stay local. A test refits from the reference data and checks the file is reproduced byte for byte. Shared-range RMS against the traced curves: 0.0261 D (250D) and 0.0252 D (500T); per-layer range 0.0213 and 0.0210.
- **Not used by the engine yet:** the bundled default stock (`emulsion-default`) is unchanged and not fitted. The fitted files sit in the offline target until MOV-25 decides how fitted stocks are bundled (under neutral ids).

- **What is fitted today:** only the negative characteristic curves. Per layer, density = minimum density + `FilmModel.negativeDensity` (the engine's own curve, not a copy) of log10 exposure minus a mid-gray anchor. Two parameterisations are always run: a shared density range (10 parameters; the one written to the stock file, since `FilmStock.Negative` holds one range) and a per-layer range (12; diagnostic for MOV-25). Everything else in the written stock is the base stock's hand-tuned values.
- **Frame:** density in the chart's densitometry (Status M for the camera negatives) against the chart's log10 exposure in lux-seconds. The mid-gray anchor defaults to camera stop 0 on the chart, an approximation; it shifts the exposure offsets but not the fit quality. Minimum densities (base + fog + mask) are fitted but not stored: the calibrated printer lights absorb a constant per-layer density.
- **What the numbers mean:** RMS and max residuals (measured − fitted density) say how closely the engine's symmetric logistic follows the *traced* curves; mean residuals per exposure third show systematic shape misfit. Standard errors are fit statistics, σ²·(JᵀJ)⁻¹; none of these numbers include the digitizing error (manifest `uncertainty`; docs/STOCK-DATA.md, "Digitized curves") or how the publisher drew the chart. A good fit to a datasheet curve is not a measurement of film.
- **Minimum density on its bound:** the fitted value is then not a reading of the film's base density (the logistic's long toe absorbs it); the report, summary and stock notes say so and give the lowest traced density. Each layer also reports its straight-line gamma (least-squares slope over the middle third of its traced density span) next to the logistic's centre slope.
- **Acceptance and caveats in the report:** the 0.03 D RMS target is MOV-106's for 250D only (`NegativeFitReport.targetStock`); other stocks are compared with it, not judged. Each layer reports how many fitted samples lie in the manifest's interpolated or shared-line spans (fitted with full weight, not dropped). Standard errors count only the parameters not on a bound (σ² = SSR / (n − p_free)).
- **Stock name:** the written stock is named `"<base name>, fitted negative"` (or `--name`); the datasheet and publisher stay in provenance, never in the name (MOV-92).
- **Solver:** plain Swift (Cholesky for the normal equations, at most 12 unknowns), so the package needs no unsafe compiler flags and stays usable as a remote dependency.
- **Determinism:** no randomness and sorted-key JSON, so the same data gives byte-identical stock files and reports (`--fit-date` is the only date written).

### Dye set and printing density

`emulsion-fit dyes --stock <id> --out <dir> [--standards <dir>] [--data <dir>] [--manifests <dir>]` (MOV-88) reconstructs a camera negative's dye set from its spectral dye density chart and converts its neutral scale to printing density. It writes `<stock>.dye-set.json` (everything), `<stock>.dye-set.md` (the summary tables, also printed) and `<stock>.neutral-scale.csv`. Every number is computed from the digitized datasheet through the standards' responsivities; none is a measurement of film.

- **Model** (FILM-THEORY §1.2, §2, §3.3): D(λ) = Dmin(λ) + Σ c_k ε_k(λ), with the sheet's "D-mins subtracted" dye curves as ε_k (net of the masking coupler each dye consumes) and its minimum-density curve as Dmin (base + fog + unused couplers). Integral density is ST 2065-2 Eq. 1 on a 5 nm grid, 360–800 nm.
- **Hold-end assumption:** outside a curve's traced span its end value is held. The report gives the effect of zero-filling the dyes instead; it is small for Status M and the dye amounts but up to 0.1 D in APD and 0.6 D in RP 180 blue at high density, because RP 180 blue and APD respond below the yellow dye's traced start.
- **What is computed:** the midscale reconstruction (least-squares dye amounts against midscale neutral − Dmin at 10 nm within 400–700 nm, where all five curves are traced; target max |residual| ≤ 0.05 D, via `DyeSumCheck`); Status M, APD and RP 180 of the minimum-density spectrum against the chart's lowest densities; the dye amounts along the neutral scale (Newton on Status M above Dmin, analytic Jacobian); straight-line gammas of Status M, dye amounts, APD, RP 180 and ADX-scaled APD; and linear conversions PD ≈ P·c, PD ≈ P·c + b, PD ≈ M·SM and PD ≈ M·SM + b for APD and RP 180, fitted on the neutral scale plus a 9×9×9 lattice of dye amounts (the Status M fits also on the neutral scale alone), with unweighted residuals on both.
- **The engine's printing-density matrix** is APD PD ≈ P·c + b with each neutral-scale row of the fit weighted 10 (`PrintingDensityConversion.engineNeutralScaleWeight`): the neutral scale sets tone and gray balance, and the calibrated printer lights absorb the offset b. For 250D, P ≈ [[0.919, 0.079, −0.002], [0.112, 0.851, 0.094], [0.053, 0.073, 0.850]] (rows APD R, G, B; columns cyan, magenta, yellow); it misses the neutral scale by at most 0.004/0.006/0.002 D and the lattice by RMS 0.006/0.024/0.012 D. Unweighted, the neutral scale misses by up to 0.017 D (green) for a lattice RMS only up to 0.004 D lower; at weight 100 the lattice RMS grows to 0.04/0.07/0.03 D. The report and summary give this sweep (w = 1, 10, 100) and the Status M 3×3 against 3×3 + offset.
- **Standards tables are local only** (not committed; MOV-94): ISO 5-3:1995 Table 4 (Status M, read from the public ANSI/NAPM IT2.18-1996 copy), SMPTE ST 2065-2:2020 element a (APD) and SMPTE RP 180-1999 Table 1. `--standards`, else `EMULSION_STANDARDS_DIR`, else `standards` beside the resolved reference-data directory (by default `~/Documents/Emulsion Research/standards`). Like the traced curves, they are needed; `dyes` fails naming the path it tried. `Resources/standards-manifest.json` records each file's standard, edition, table, source URL and SHA-256; loading fails on a missing file or a checksum mismatch. Tests that need the tables skip unless both the reference data and the standards directory exist.

## Non-film looks: Digicam 2004

A curated look ("Digicam 2004", MOV-149) that renders a photo like the in-camera JPEG of a mid-2000s compact CCD camera. It is not a film process: no negative, no print, no printer lights. It is a separate, deterministic render path beside negative → print, so the film model stays honest about what it models and the camera look can be measured against cameras rather than stocks. After the owner's review the look is deliberately stronger and more washed out than the period measurements in places (lower dynamic range, a stronger white-balance cast, more noise, harder sharpening, heavier JPEG); the constants table says where it departs from a measurement.

**Where it plugs in.** `RenderProcess` (`film`, `digicam`) is stored on `Adjustments.process` (a library index without it, or with a process this version doesn't know, renders film rather than failing to load). Downgrade caveat: an older app that re-saves the library drops `process`, so digicam edits revert to film after a downgrade. A recipe carries the process as its `engineModel` (`RenderProcess.engineModel`): film keeps `emulsion-default-v1`, so film recipe files are byte-for-byte unchanged, and digicam is `emulsion-digicam-v1`; an app that predates a process refuses its recipes (`recipeModelUnsupported`) instead of printing them as film. The process reuses Grain as Noise and Halation as Processing so the recipe format stays at version 1 (`docs/DECISIONS.md`, 14 Nov 2026). `CuratedLooks` has the look (id …0005). `Renderer.render(_:_:intent:)` dispatches to `Renderer+Digicam.swift`; `RenderIntent` (`preview`, `export`) says what a render is for, and only the digicam process uses it. Constants are `DigicamLook`, the pointwise maths and its Swift mirror `DigicamModel`, the kernels `Kernels/Digicam.ci.metal` (`DigicamKernels`), linked into the same metallib as the film kernels.

**Graph** (working space extended linear sRGB; "processing" is the Processing amount, 0…1):
1. *Sensor frame.* Centre crop to 4:3 (landscape or portrait, as the source), output at the origin; if the long edge exceeds 2592 px it is Lanczos-downscaled to 2592 × 1944 (5.0 MP). Smaller renders (previews) keep their size. Spatial sizes are in sensor pixels × (output long edge / 2592), so a preview is close to a downscale of the export; blurs under 0.5 output px are skipped.
2. *Lens*, scene light: purple fringing when processing is on (a mask of light above 85 % of the clip, blurred by σ 3.5 px, minus itself, tinted violet, added × processing, so dark edges against clipped light such as white cloud fringe); a whole-frame softness (σ 0.8 px) blended towards the corners (weight r²) into a blur of σ 3 px × processing, never less than the whole-frame σ, so the corners are never sharper than the centre; a vignette of 1 stop × processing at the corners (∝ r²).
3. *White balance and exposure:* von Kries channel gains in linear sRGB, normalised to luminance 1, times 2^exposure. The develop already neutralised the light; the simulated auto white balance corrects only 60 % of the distance in mireds from 5500 K to the RAW file's as-shot temperature, so the gains are the light's Planckian sRGB (Kim et al. 2002 chromaticity, `ColorMath.planckianChromaticity`) over the camera's white. Tungsten stays orange, shade cool; a constant cool bias (12 mired, a touch of magenta) leaves daylight cool cyan-blue, and the Warmth/Tint controls shift the camera's white. Photos that aren't RAW get the bias and Warmth/Tint only. The residual uses the as-shot temperature (`Negative.asShotWhiteBalance`, which a develop and a kept `RAWDecoder` report whatever white balance they develop at). A white balance set at develop (the White Balance rulers) is applied on top: the develop neutralises the light it is set to, in camera space, and the same residual cast is then added, so moving the rulers away from as shot shifts the picture from the camera's cast, and as shot gives exactly the camera's cast.
4. *Sensor:* noise in linear before the clip, σ ∝ √(signal / clip) plus a read floor that dominates the shadows: per-pixel luminance noise and blotchy per-channel noise (value noise in 6 px cells; being independent per channel it adds luma noise as well as colour), blue × 1.25, deterministic per `seed`, attenuated below a pixel like film grain. Then a hard per-channel clip 2 stops over mid-gray (per-channel clipping gives the hue-shifted blown skies of small sensors) and a black offset 4.5 stops under mid-gray.
5. *Colour:* luma-preserving saturation in linear light, 1.15 × the Color control.
6. *Tone:* the JPEG curve on light / clip: sRGB encode, a power that puts mid-gray on the pivot, a gentle S curve (15 % of a square on each side) whose slope at the clip is 0.85, so highlights reach white at the clip with no shoulder, then lifted so black is code 22 and mid-gray lands on code 118. Output is display-linear sRGB in 0…1 (sRGB gamut, as the cameras wrote).
7. *Local tone* (Highlights/Shadows, the film path's kernel) when set.
8. *Sharpening:* unsharp mask on gamma-encoded luma (σ 1.8 px, amount 1.85 × processing), clipped to 0…1, so edges carry thick bright and dark halos.
9. *JPEG:* exports only (`RenderIntent.export`), when processing is on, at whatever size the output is: a real Core Image JPEG encode and decode in sRGB at quality 0.9 − 0.4 × processing, through the same encoder path as `Renderer.export` (metadata cleared, MOV-126). Previews skip it: at their size the 8 × 8 blocks would be sub-pixel. A digicam export is therefore encoded twice: the camera's JPEG round trip here, then the export's own format (JPEG at 0.95, or 10-bit HEIC), so the file format stays the app's choice. The second encode is a known, small generation loss on top of the simulated one.

**Controls in the digicam process.** Exposure is set before the sensor clip. Warmth and Tint shift the camera's white balance (60 mired and 12 % green gain per unit), not printer lights. Color scales the saturation. Highlights/Shadows are the same local tone, after the tone curve. Grain is the sensor noise ("Noise" in the editor). Halation is the in-camera processing ("Processing": fringing, corner softness, vignette, sharpening and JPEG strength scale with it; 0 is clean apart from the lens's overall softness). Defaults: noise 0.75, processing 0.7; the review renders' "digicam-strong" is noise 1, processing 1.

The library and editor show the 4:3 frame the process makes. Not modelled: per-hue colour errors, demosaic artefacts, lens distortion, CCD smear and blooming, in-camera noise reduction.

## Roadmap, in order of colorist value

1. **Output transforms.** Explicit display encodings: Rec.709 BT.1886 2.4, sRGB, P3-D65 2.6, and HDR Rec.2100 PQ/HLG rendered from the film state before the SDR clip (re-expanding an already-clipped print shoulder doesn't work).
2. **Video.** AVAssetReader / AVPlayerItemVideoOutput pixel buffers enter as raw code values (no color matching) → input transform → Renderer → AVAssetWriter (HEVC 10-bit, ProRes 422). Add gate weave and flicker as optional temporal texture.
3. **LUT export.** Bake input transform → film system → output transform into 33³/65³ `.cube` LUTs for Resolve/Baselight/Premiere. Spatial effects (grain, halation, local tone) can't be LUTs and are listed as excluded.
4. **Stocks from public data.** Fit the negative and print model parameters to Kodak's published datasheet curves (Vision3 250D/500T characteristic and spectral-sensitivity curves; 2383 print), with a fitting report. Add lab controls: push/pull, printer-light points, print density, bleach-bypass (silver retention).
5. **Colorist tools.** True RAW white balance (kelvin/tint in camera space via `CIRAWFilter`) is done in the engine and `RenderService` (MOV-10), with Temperature and Tint rulers in the editor on a kept-alive decoder (MOV-137, see [RAW white balance](#raw-white-balance)). RAW decoder 9 is not used (see [RAW white balance](#raw-white-balance)). Next: acutance (edge contrast) and aura; scopes (waveform, parade, vectorscope) driven from the same render.
6. **UI.** SwiftUI with iOS 26 Liquid Glass. Simple by default: one look, Light / Color / Texture. Depth on demand. Native iPhone Duo layouts once Xcode 27.1 is installed.

## What we deliberately don't do

- No copying of another product's looks, data, code or branding. Chromagraph and Filmbox are references for *what* colorists value, not sources.
- No claims of matching any specific film or product without a measured comparison.
