# Emulsion engine

Emulsion is a film lab for colorists. It takes camera RAW, log and HDR video, and ordinary JPEG/HEIC/MP4. RAW and log are decoded into **scene light**; HLG is decoded as nominal scene light; ordinary JPEG/HEIC only gets an estimate of scene light, because the phone's rendering can't be undone, and is printed relative to itself (see [Input contracts](#input-contracts)). The result is printed through a modeled photochemical system. The look comes from a negative → print chain behaving like one. It is not a stack of filters or a LUT.

The UI should stay simple, while the engine underneath is something a colorist can trust: it's measured, its stages are documented, and the GPU output is verified against a reference model.

## Architecture

```
source ──▶ input transform ──▶ scene light (linear, 0.18 = mid-gray) ──▶ grade ──▶ film system ──▶ output
          RAW develop         one working space for every source          exposure   negative → print   P3 today;
          log / HLG curves                                                  halation   printer lights     Rec.709 2.4,
          display estimate                                                  local tone grain              PQ/HLG next
```

| Stage | File | What it does |
| --- | --- | --- |
| RAW develop | `Developer.swift` | Apple `CIRAWFilter` with Apple's rendering switched off: no boost, local tone map, extra contrast, extended dynamic range, gamut mapping or shadow bias. Gamut mapping was what capped highlights near 1.0, so turning it off keeps their headroom and lets out-of-gamut colours stay negative for the film model. Highlight recovery stays on, so clipped channels are estimated and blown highlights stay neutral. The result is demosaiced, white-balanced, linear scene light scaled by the file's BaselineExposure (MOV-79) and then by one per-file exposure anchor (MOV-134, see [Exposure anchor](#exposure-anchor)). White balance is applied here, in the camera's colour space, by `CIRAWFilter` (`neutralTemperature`/`neutralTint`): as shot unless `Adjustments.whiteBalance` sets a temperature and tint (MOV-10, see [RAW white balance](#raw-white-balance)). It is separate from the printer-light Warmth and Tint, which act at print. ImageIO types many ProRAW files read from memory as plain TIFF, so files are identified, and handed to `CIRAWFilter`, with a DNG type hint |
| Input transforms | `ColorSpaces.swift`, `VideoSignal.swift`, `inputTransform` / `ycbcrInputTransform` kernels | Apple Log, S-Log3/S-Gamut3.Cine, ARRI LogC3/LogC4, V-Log, DaVinci Intermediate/DWG, ACEScct (Bradford from ACES white), HLG (BT.2408 scaling), Rec.709 and Display P3 display encodings. Code values become the BT.2100 signal E′ using the declared range (legal or full); 10-bit Y′CbCr frames use their tagged matrix (BT.709 or BT.2020). S-Log3, LogC3 and V-Log formulas take 10-bit legal-range code values, the rest take E′ |
| Display-referred sources | `FilmModel+Display.swift`, `displayToScene` and `filmSystemRelative` kernels | JPEG/HEIC/Rec.709/Display P3 get a scene estimate through the film's own neutral print response, with soft ends so display white and black land on a finite ceiling (+4 stops) and floor (−6 stops). At render time the change the film predicts for the user's edits is applied to the photo itself, so zero edits reproduce it and edits act like the film would on that estimate. Where the photo is darker than the film's own print of it (ratio g < 1), a lift lets a zero channel rise when brightening; when darkening the lift is scaled so the slope stays continuous through zero edits for g ≥ 0.382 and the output never goes negative or reverses (`FilmModel.relative`). It is a re-render, not a recovery of the scene (see Input contracts) |
| Film system | `FilmModel.swift`, `filmSystem` kernel | Layer sensitivities (crosstalk) → negative characteristic curves in dye amount (toe and shoulder, fitted to the 250D datasheet) → printing density through the dye set's printing-density matrix → printer lights → print H&D curves (Richards toe) → print dye cross-absorption → 10^−density relative to paper white. Mid-gray is calibrated neutral, like a timing lab |
| Highlight chroma retention | same | The one non-physical step. Bright saturated light (neon) blends toward a ratio-preserving render above +1.5 stops, so it doesn't band. Midtones are unaffected; timed (warm/cool) neutrals above +1.5 stops lose part of their timing, and very bright saturated colors stay tinted instead of reaching white (artistic choice under review) |
| Halation | `Renderer.swift` | Scene highlights above about +3.5 stops add red-orange glow (core + skirt) back into exposure, before the negative. Blurred at reduced scale with energy-preserving box halving |
| Local tone | `LocalTone.swift` | Halo-free Highlights/Shadows: a box-averaged base layer with edge-preserving upsampling (carried over from the GradingCore study; the current test allows ≤3 codes of halo) |
| Grain | `grain` kernel | Density noise on perceptual lightness, peaking in the midtones. The cell size is relative to the image, and sub-pixel cells are attenuated, so preview and export carry matching grain statistics |
| Interactive speed | `Renderer.materialize` | The developed preview is rendered once into a half-float buffer, so slider moves never re-run the RAW develop or the JPEG inversion |

## Input contracts

Not every input can tell us what the scene looked like. Each source has a contract: what its decoded values mean, and what the engine may say about them. In code the contract is `InputContract`, declared by each input on `InputColorSpace.contract` and carried by every developed image on `Negative.contract`.

| Source | Contract | What the engine does | What it may claim |
| --- | --- | --- | --- |
| RAW (Bayer DNG, ProRAW) | Scene-referred | Apple `CIRAWFilter` with Apple's look switched off | Linear scene light from Apple's develop. ProRAW is already computational photography, so "scene light" means Apple's linear develop, not a sensor measurement. Highlight headroom is MOV-79. Overall exposure follows the file's DNG profile through the exposure anchor (MOV-134), an estimate, not a metered level |
| Camera log (Apple Log, S-Log3, LogC3/LogC4, V-Log, DaVinci Intermediate, ACEScct) and linear P3 | Scene-referred | The manufacturer's published curve and gamut matrix | Scene light; the decode is verified against colour-science references |
| HLG (Rec.2100) | Nominal scene | BT.2100 inverse OETF with BT.2408 scaling | Decoded as scene light by the standard, but phone HLG is rendered by the camera before encoding, so it is not claimed to be the scene |
| JPEG, HEIC, Rec.709, Display P3 | Display-referred | Scene estimate from the neutral print response (soft ends at the top and bottom), then printed relative to the photo | A re-render of the photo, not the scene. Zero edits reproduce it: gray codes 0–255 within 1 code (measured 0.06), a real 8-bit JPEG of mild chroma within 0.25 codes of its own decode (measured 0.07). For colors near the P3 boundary the output gamut fit lowers chroma, to 94% at the primaries (OKLab ΔE×100 up to 2.1; on a saturated gradient a low channel rose by up to 10 codes); lightness and hue are kept. Display white is estimated at +4 stops, black at −6 stops (see "Display black" below); the ceiling, the floor and the two knees (display-linear 0.75 and 0.006) are engineering choices, not measurements. Limits: edits act on an estimate; the Color control acts more weakly on extremely saturated source colors; 8-bit sources still quantize; HDR headroom is discarded (MOV-49); halation is driven by the estimate, so a clipped white glows like a +4-stop light (peak glow source 0.72, computed from the halation source at the estimate; the earlier unbounded inverse gave about 4) |
| Camera viewfinder frames (the camera's processed video) | Preview estimate | `Developer.viewfinderNegative(from:)`: the display-referred scene estimate, approximated by a 1D curve sampled once from the Swift mirror (built-in `CIColorCurves`, 1024 steps in extended Display P3 encoding) and the inverse layer sensitivity (`CIColorMatrix`), with no per-pixel solve; then printed absolutely, like the RAW capture it previews | A preview of the RAW render made from the camera's processed video frame, never scene light. Its print is within OKLab ΔE×100 0.04 of printing the exact estimate (`ViewfinderEstimateTests`). How far it is from the captured photo (Apple's video tone mapping, white balance, noise reduction, clipping) is unmeasured until device testing (MOV-121). Preview only: never exported or stored |
| HDR stills (gain-map HEIC/JPEG, PQ/HLG HEIF) | Display-referred | Read as their SDR rendition (the gain map is ignored; PQ/HLG are tone-mapped by Core Image), then as above | Same as display-referred; HDR headroom is discarded until MOV-49 |

**Display black.** Display black is given the scene estimate of a `FilmLook.displayFloorStops` light, so the soft ends map display 0 onto the print's black F_n(floor). The fitted toe-and-shoulder negative (MOV-25) leaves the neutral print almost flat below about −6 stops (F_n = 0.00200 at −10, 0.00224 at −6, 0.00273 at −5), so a deeper floor puts display codes 0 and 1 stops apart and a lifting edit separates them (banding). The floor is the deepest value on the grid −9, −8, −7.5 … −5 whose largest adjacent-code step on an 8-bit gray ramp (codes 0…24, Display P3, rendered on the GPU) stays within 1.1× the logistic negative's (2.94 at +2 EV, 4.63 at +3 EV, 8.95 at +2 EV with shadows +1) and monotone: an engineering choice, not a measurement. ### Exposure anchor

Bypassing Apple's rendering also drops two hints in the file's DNG profile: the ProfileGainTableMap (what `CIRAWFilter` calls local tone mapping) and the ProfileToneCurve (its boost). 12 MP ProRAW puts its brightening in BaselineExposure, which the develop keeps; 48 MP ProRAW puts 2–3 stops of it in the gain table, so without the anchor 48 MP files developed 2.0–2.9 stops darker (median) than Apple's own render.

The exposure anchor (`ExposureAnchor.swift`, reported as `Negative.exposureAnchorStops`) is one scalar per file, applied as a single linear multiply, so ratios between pixels, values above 1.0 and negative components are untouched. It is computed only when Apple can apply a gain table for the file (`CIRAWFilter.isLocalToneMapSupported`). Deliberately excluded, with anchor 0: a DNG with a tone curve but no gain table, and non-DNG RAW, where Apple's boost is its own look curve rather than the file's DNG profile (unverified on such files: no sample exists). Derivation: the filter renders a 256 px thumbnail twice, once with the develop's linear settings and once with the gain table and tone curve applied (`localToneMapAmount` and `boostAmount` at 1; on real files these match the DNG SDK's gain table within 0.025 stops and the tone curve within 0.02 stops at mid-gray). The anchor is log2 of the geometric mean of the luminance ratio (profile ÷ linear) over the pixels the profile renders within ±1 stop of 0.18; with under 1 % of pixels in that window every pixel counts; it is clamped to −2…+5 stops (measured −0.56…+2.95). The thumbnail size is fixed, so previews and exports get the same anchor (equal within 1e-6 at 1024 and 512 px on 25 files).

What it is: an estimate that places the tones the file's own profile renders at mid-gray at scene 0.18. It is not a measurement of scene reflectance. Its limits:
- The pixel selection depends on the scene: the window picks whichever pixels the profile renders near mid-gray, and the gain table changes per shot. On 25 files the anchored median lands within 0.58 stops of Apple's default render (mean absolute 0.17; files ≥ 40 MP and < 20 MP differ from it by −0.02 stops on average, where 48 MP used to sit 2–3 stops lower); for the 22 iPhone 15 Pro Max files the residual log2(anchored ÷ Apple) spans −0.28…+0.58 stops, so two shots from the same camera can be placed differently by up to about 0.85 stops relative to Apple's render.
- The profile render uses `boostShadowAmount` 1, its neutral value; Apple's default (0.9 on all 25 files) darkens shadows below about 0.12 on top of the tone curve. It has no effect on the linear develop (pixel-identical, synthetic and real files).
- The absolute level is unverified until a grey card is shot: no file in the sample set has one.
- Cost, Mac only, develop + materialize of a 1024 px preview (median ms without → with the anchor; iOS device timing, and the target phone's files, are untested): iPhone 15 Pro Max 48 MP 942 → 971, iPhone 15 Pro Max 12 MP 111 → 125, iPhone 14 Pro 48 MP 1145 → 1996, iPhone 12 Pro 12 MP 94 → 155, Pixel 8 Pro Bayer 125 → 187. It depends on the file generation and on what the process decoded before: Apple sometimes reuses a filter's RAW decode between renders and sometimes decodes again for every render (seen on the iPhone 14 Pro, iPhone 12 Pro and Pixel files when another file was developed first; developed alone, the same three cost 965, 114 and 185 ms with the anchor). The two thumbnails go through their own context that caches intermediates, so the second reuses the first's decode in every case; the output render can still pay one more decode, which no render order avoided. Full tables are in the MOV-134 PR. So the app measures it once per file: `RenderService` remembers the anchor of a file's first develop for the session and passes it back (`develop(_:maxDimension:whiteBalance:exposureAnchorStops:)`) for other preview sizes, white balances and the export, which then skip the thumbnails and cost the same as a develop without the anchor (Mac, 1024 px, median ms: iPhone 14 Pro 48 MP 1141 given vs 1145 without and 2002 measuring; iPhone 12 Pro 98 vs 96 and 155; Pixel 8 Pro 130 vs 125 and 177).

### RAW white balance

`CameraWhiteBalance` (temperature in kelvin, tint) replaces the file's as-shot white balance when a RAW file is developed (MOV-10). `CIRAWFilter` turns it into a camera neutral and white-balances in camera space, before the camera matrix, which is what a white balance at develop means; a printer-light correction after the develop cannot do this. Values are clamped to Apple's documented ranges (2000–50000 K, tint −150…150). `nil` is as shot. `Negative.asShotWhiteBalance` is what the decoder reads from the file whatever the develop was set to, for a UI to start from; it is nil for photos that aren't RAW, and `RenderService` then never develops them again for a white balance. A recipe neither stores nor changes it: it describes the light one photo was shot under.

- Order: the exposure anchor is measured at the as-shot white balance, then the new white balance is set, then the output is rendered, so the anchor does not move when the white balance does (identical on synthetic and 25 real files). Setting it after the anchor does not make `CIRAWFilter` decode the file again (the output render takes about the same time with and without a change), setting it before or after the preview scale gives identical pixels, and a develop costs the same with and without a white balance. Timings are in the MOV-10 PR.
- Previews: `RenderService` keeps one developed preview per photo and size together with the white balance it was developed at; a new white balance develops the file again, reusing its exposure anchor (measured as shot, so the same at any white balance), and replaces it, about 1 s for a 48 MP ProRAW at 1024 px on a Mac. Re-rendering a kept-alive `CIRAWFilter` at the new temperature would take about 30 ms: a follow-up for when the UI control lands.
- Apple's tint is the light's distance from the Planckian locus × 3000 (Duv in CIE 1960 uv; positive is a green light, corrected towards magenta), the DNG SDK's scale: a file tagged with D65 reads 6502 K, tint 9.77, against 6504 K and 9.52 for D65's Duv. Measured, not documented by Apple.
- Limits: the synthetic chromatic patches are lit by scaling camera channels (von Kries in camera space), not a spectral simulation, so the chromatic checks test the mechanism, not how a real sensor sees colour under tungsten. The 22 iPhone 15 Pro Max samples are Lightroom re-saves, so on them only the mechanism is tested.

**RAW decoder 9 is not used.** `CIRAWFilter.decoderVersion` stays at the file's default, which is "8.dng"/"8" on all 25 real DNGs and on the synthetic ones: decoder 9 is opt-in (WWDC26 session 305, "What's new in Core Image RAW"; the SDK header's "newest available" does not match what the filter reports). On the same files decoder 9 changes the image a lot: the iPhone 14 Pro 48 MP file's mean RGB goes from (0.1485, 0.1724, 0.1883) to (0.0248, 0.0202, 0.0118), medians move both ways from file to file, and synthetic Bayer neutrals develop with a warm tint (R/G 1.04–1.22). Apple DTS forum thread 843445 reports colour problems with it too. Until it develops neutrals neutral and keeps the exposure, the develop stays on the default decoder (measured on macOS 27.2, MOV-10).

**Sub-black policy.** Decoding keeps sub-black signals (legal-range footroom, compression undershoot) as negative light; clipping is the film model's job. Where a specification defines values below its range, the engine follows it: Apple Log holds at R₀, and the log curves' toes and sRGB's linear segment extend linearly. Where it doesn't (BT.2100 HLG, BT.1886 gamma 2.4), the curve is extended oddly (mirrored), so every decode stays monotonic through black. colour-science mirrors HLG the same way; for BT.1886, which colour-science clamps, the reference generator applies the engine's convention.

## Stock files

A stock's parameters live in a JSON stock file, not in code. `FilmStock` (`FilmStock.swift`) is the file format; `FilmModel(stock:)` turns it into the immutable model the renderer and kernels use.

- **Format** (`formatVersion` 2): `name`; `provenance` (`source`, `notes`, and optional `fitDate`, `tool`, `sourceStock` (the fit tool's id of the datasheet stock fitted; committed fits only, never the shipped default), `sourceSHA256`, `fitResiduals`, omitted when absent); `negative` (`sensitivity` 3×3, `gamma`, `toeExposure`, `toeWidth`, `shoulderExposure`, `shoulderWidth`, `printingDensity` 3×3); `print` (`gamma`, `minimumDensity`, `densityRange`, `shape`, `dyes` 3×3); `rendering` (`highlightChromaRetention`, `middleGrayOut`). Matrices are three rows of three, row-major. The negative's curve is dye amount above minimum density, c(x) = gamma·[toeWidth·softplus((x − toeExposure)/toeWidth) − shoulderWidth·softplus((x − shoulderExposure)/shoulderWidth)], x the log10 exposure relative to mid-gray: zero far below the toe, a straight line of slope `gamma` between toe and shoulder, flat far above the shoulder. `printingDensity` maps the cyan, magenta and yellow amounts (columns) to printing density R, G, B (rows); the print sees `printerLights + lights − printingDensity·c`. Print gammas are density per log10 print exposure. `encoded()` writes sorted keys, so a stock always encodes to the same bytes. Version-1 files (logistic negative, no matrix) are rejected, naming the version; the only one was the old default.
- **Validation** (`EmulsionError.invalidStock` with the reason): unknown `formatVersion`, wrong array lengths or missing keys; non-finite numbers; gammas, toe and shoulder widths, print density range or print shape ≤ 0; a shoulder exposure not above its toe exposure; a printing-density matrix with a diagonal entry ≤ 0 or a zero determinant (it has no row-sum rule: it is a fitted density conversion, not a neutral-preserving mix); a component of printingDensity·gamma ≤ 0 (a channel whose printing density doesn't rise with neutral exposure); a negative curve that falls anywhere the engine reaches, log10 exposure from log10(1e-7/0.18) ≈ −6.26 (the layer-exposure floor, `FilmModel.layerExposureFloor`, the kernel's 1e-7) to +6 (about +20 stops, beyond any exposure the pipeline produces): the slope is gamma·[σ(z_t) − σ(z_s)], non-negative exactly where z_t ≥ z_s, and z_t − z_s is linear in x, so both ends are checked; negative minimum density; `middleGrayOut` outside (0, 1); `highlightChromaRetention` outside [0, 1]; sensitivity or dye rows not summing to 1 (±1e-6; that is what keeps neutrals neutral); and a print the printer lights can't time, meaning mid-gray misses `middleGrayOut` by more than 1e-6. `errorDescription` is the plain localized sentence; the reason is `failureReason`.
- **Default:** `Resources/Stocks/emulsion-default.json`, loaded once as `FilmLook.stock`. Its negative curves and `printingDensity` are `emulsion-fit negative`'s fit of the 250D datasheet (H-1-5207), regenerated from the default itself with `swift run emulsion-fit negative --stock kodak-vision3-250d-5207 --out <dir> --fit-date <date> --bundled-default Sources/EmulsionCore/Resources/Stocks/emulsion-default.json`, which writes the committed fit (`<dir>/kodak-vision3-250d-5207.stock.json`, copied to `StockData/kodak-vision3-250d-5207/negative-fit.stock.json`) and the default from the same run. The default is that fit with the name "Emulsion Default" and a brand-free provenance (`FittedStock.bundledDefault(from:)`): the apps ship it, and no film brand goes into the product (MOV-92), so its `source` names no publisher, title, URL or stock id and points to the committed fit through `sourceSHA256`; date, tool, residuals and notes are kept. The committed fit, which is not shipped, keeps the datasheet's full provenance. A test that always runs checks the default's `negative`, `print` and `rendering` equal the committed fit's exactly, its `sourceSHA256` matches, and its file contains no brand word; with the local data, a test reruns the tool and checks both files are reproduced within 1e-9 (a fixed point). The print gammas are rebalanced per channel to K / (printingDensity·gamma) with K = 1.33, the print × negative gamma product of the previous hand-tuned default: a print stock's layer contrasts are matched to the printing-density contrasts of the negatives it prints (SMPTE RP 180-1999 Introduction; the 2383 sheet's mid-scale slopes R 3.69 / G 3.25 / B 3.46 times the fitted 250D printing-density gammas give 1.87 / 1.88 / 1.81); without it the gray scale turns green/magenta by up to 5% away from mid-gray. K itself is artistic (MOV-5). Sensitivity, the rest of the print and the rendering choices are hand-tuned. A test pins its render at five chromatic inputs.

## Digitized stock data

The offline `EmulsionFit` target (never linked into an app, not a library product) holds a manifest per digitized stock in `Sources/EmulsionFit/Resources/StockData/<stock>/`, naming the PDF (with its SHA-256), page, conditions, axis calibration, the per-point reading error and the SHA-256 of each traced CSV, plus the fitted stock files (see "Fitting stocks"). The traced curve CSVs are not in the repository (`docs/DECISIONS.md`, 12 Nov 2026): anyone with the public PDF can re-trace them with `Tools/stock-digitizing/digitize.py`. They are local reference data, read from `EMULSION_REFERENCE_DATA` or else `~/Documents/Emulsion Research/datasheet-tracings`; the loader refuses any CSV whose digest differs from its manifest. Where that folder is missing, only the manifest checks run. `docs/STOCK-DATA.md` ("Digitized curves") covers the method, the error estimates and the cross-check.

- **Manifest checks on load:** the manifest's `stock` must match its directory, and grid steps, pixel scales, uncertainties, x ranges, spans and the camera-stop anchor must be finite and in range, or loading fails naming the field.
- **Audit:** samples sit on the manifest's grid and inside each curve's traced extent, and characteristic curves never fall by more than one chart pixel of density.
- **Dye-sum check** (MOV-17): the yellow, magenta and cyan dye spectra, with non-negative least-squares scales, against the sheet's neutral; target max |residual| ≤ 0.05 D. Dye densities are used as drawn, negative lobes included (the negatives' magenta dye dips below zero near 445 nm). Negatives: the acceptance compares neutral − minimum density, because the dye curves are drawn "D-mins subtracted" while the neutral and minimum-density spectra are drawn as measured; the unsubtracted comparison is reported as a diagnostic. Print film: the acceptance compares the visual neutral over 400–700 nm, where the three image dyes account for it; the full overlap and the scales-fixed-to-1 residual (with its mean) are diagnostics. With scales fixed to 1 the neutral sits above the plain dye sum by a roughly flat amount over 400–700 nm and rises steeply below 400 nm; the chart does not say what the extra density is.

## Fitting stocks

`emulsion-fit` (target `EmulsionFit`, offline only, never linked into an app) fits stock parameters to the digitized datasheet charts described above. It reads the manifests (bundled, or `--manifests <dir>`) and the traced curves from the reference data (`--data <dir>`, else `EMULSION_REFERENCE_DATA`, else the default folder); `check` and `negative` stop with an error when there is none.

- **Committed fits:** `StockData/<stock>/negative-fit.stock.json` for 250D and 500T, written by `emulsion-fit negative --stock <id> --out <dir> --fit-date 2026-11-12` (default base and name). They hold parameters, provenance (including the characteristic CSV's SHA-256) and residual statistics only; the fit report and plot table contain traced samples and stay local. CI checks that each passes the engine and names its tracing; where the local data exist, a test refits and checks the file is reproduced within 1e-9 (debug and release builds differ in the last digits). Toe-and-shoulder Status M RMS per layer R/G/B: 0.0023/0.0026/0.0040 D (250D) and 0.0021/0.0029/0.0045 D (500T).
- **Used by the engine:** the bundled default is the 250D fit (see "Stock files" above); it differs from the committed fit only in name and provenance (brand-free, `--bundled-default`). The 500T fit is not bundled: bundling more fitted stocks under neutral ids is a later decision.

`emulsion-fit negative --stock <id> --out <dir> [--standards <dir>] [--data <dir>] [--manifests <dir>] [--base <stock.json>] [--mid-gray-log-exposure <x>] [--fit-date <date>] [--name <text>] [--bundled-default <file>]` writes `<stock>.stock.json`, `<stock>.negative-fit.json` and `<stock>.negative-fit.csv` and prints the summary; `--bundled-default` (250D only) also writes the engine's bundled default to `<file>`. It needs the standards tables (see below).

- **What is fitted:** the dye set (next section) turns the chart's neutral scale into dye amounts above minimum density, per layer; each layer's amounts are fitted, by bounded least squares, with d0 + `FilmModel.negativeDyeAmount` (the engine's own curve; d0 is a small offset, fitted but not stored, since the printer lights absorb a constant density). The engine's printing-density matrix (below) is written with it. Everything else in the written stock is the base stock's, except the print gammas, rebalanced to the base's print × printing-density gamma product per channel (so regenerating the default from itself is a fixed point).
- **Comparison:** the engine's previous symmetric logistic, d0 + range·logistic(4·gamma/range·(x − center)) with a per-layer range, is fitted to the same amounts and reported, never written. Its centre slope overstates the straight-line gamma by about 10%.
- **Residuals,** per layer and form, as RMS, max |r| with its log exposure, and toe/middle/shoulder third means: (a) in dye amount; (b) in the chart's own densitometry, traced Status M − [lowest traced density + Status M of the dye stack at the three layers' fitted amounts]. (b) is MOV-25's acceptance, RMS ≤ 0.03 D per layer, judged on 250D only (`NegativeFitReport.targetStock`). Standard errors are fit statistics, σ²·(JᵀJ)⁻¹ over the parameters not on a bound; none of these numbers include the digitizing error or how the publisher drew the chart. A good fit to a datasheet curve is not a measurement of film.
- **Result (Approximated: right mechanism, fitted parameters):**

  | | toe-shoulder dye-amount RMS | Status M RMS | logistic Status M RMS |
  | --- | --- | --- | --- |

  | 500T | 0.0023 / 0.0024 / 0.0049 | 0.0021 / 0.0029 / 0.0045 | 0.017 / 0.022 / 0.024 |

- **The shoulder:** the fitted shoulder exposure lies inside the traced range, 0.4–1.0 stops below the last traced sample (+7.97 stops on 250D, +8.25 on 500T). What is extrapolated is the curve beyond the last traced point, its flat top.
- **Also reported:** straight-line gammas (Status M, dye amounts, APD), the last traced exposure, and the printing-density matrix with its residuals. Each layer reports how many fitted samples lie in the manifest's interpolated or shared-line spans (fitted with full weight).
- **Frame:** the chart's log10 exposure in lux-seconds; the mid-gray anchor defaults to camera stop 0 on the chart, an approximation that shifts the exposures but not the fit quality.
- **Stock name:** the written stock is named `"<base name>, fitted negative"` (or `--name`); the datasheet and publisher stay in provenance, never in the name (MOV-92).
- **Solver:** plain Swift (Cholesky for the normal equations, at most 6 unknowns per layer), so the package needs no unsafe compiler flags and stays usable as a remote dependency.
- **Determinism:** no randomness and sorted-key JSON, so the same data gives byte-identical stock files and reports in one build (`--fit-date` is the only date written); debug and release builds differ in the last digits (up to 4e-12).

### Dye set and printing density

`emulsion-fit dyes --stock <id> --out <dir> [--standards <dir>] [--data <dir>] [--manifests <dir>]` (MOV-88) reconstructs a camera negative's dye set from its spectral dye density chart and converts its neutral scale to printing density. It writes `<stock>.dye-set.json` (everything), `<stock>.dye-set.md` (the summary tables, also printed) and `<stock>.neutral-scale.csv`. Every number is computed from the digitized datasheet through the standards' responsivities; none is a measurement of film.

- **Model** (FILM-THEORY §1.2, §2, §3.3): D(λ) = Dmin(λ) + Σ c_k ε_k(λ), with the sheet's "D-mins subtracted" dye curves as ε_k (net of the masking coupler each dye consumes) and its minimum-density curve as Dmin (base + fog + unused couplers). Integral density is ST 2065-2 Eq. 1 on a 5 nm grid, 360–800 nm.
- **Hold-end assumption:** outside a curve's traced span its end value is held. The report gives the effect of zero-filling the dyes instead; it is small for Status M and the dye amounts but up to 0.1 D in APD and 0.6 D in RP 180 blue at high density, because RP 180 blue and APD respond below the yellow dye's traced start.
- **What is computed:** the midscale reconstruction (least-squares dye amounts against midscale neutral − Dmin at 10 nm within 400–700 nm, where all five curves are traced; target max |residual| ≤ 0.05 D, via `DyeSumCheck`); Status M, APD and RP 180 of the minimum-density spectrum against the chart's lowest densities; the dye amounts along the neutral scale (Newton on Status M above Dmin, analytic Jacobian); straight-line gammas of Status M, dye amounts, APD, RP 180 and ADX-scaled APD; and linear conversions PD ≈ P·c, PD ≈ P·c + b, PD ≈ M·SM and PD ≈ M·SM + b for APD and RP 180, fitted on the neutral scale plus a 9×9×9 lattice of dye amounts (the Status M fits also on the neutral scale alone), with unweighted residuals on both.
- **The engine's printing-density matrix** is APD PD ≈ P·c + b with each neutral-scale row of the fit weighted 10 (`PrintingDensityConversion.engineNeutralScaleWeight`): the neutral scale sets tone and gray balance, and the calibrated printer lights absorb the offset b. For 250D, P ≈ [[0.919, 0.079, −0.002], [0.112, 0.851, 0.094], [0.053, 0.073, 0.850]] (rows APD R, G, B; columns cyan, magenta, yellow); it misses the neutral scale by at most 0.004/0.006/0.002 D and the lattice by RMS 0.006/0.024/0.012 D. Unweighted, the neutral scale misses by up to 0.017 D (green) for a lattice RMS only up to 0.004 D lower; at weight 100 the lattice RMS grows to 0.04/0.07/0.03 D. The report and summary give this sweep (w = 1, 10, 100) and the Status M 3×3 against 3×3 + offset.
- **Standards tables are local only** (not committed; MOV-94): ISO 5-3:1995 Table 4 (Status M, read from the public ANSI/NAPM IT2.18-1996 copy), SMPTE ST 2065-2:2020 element a (APD) and SMPTE RP 180-1999 Table 1. `--standards`, else `EMULSION_STANDARDS_DIR`, else `standards` beside the resolved reference-data directory (by default `~/Documents/Emulsion Research/standards`). Like the traced curves, they are needed; `dyes` fails naming the path it tried. `Resources/standards-manifest.json` records each file's standard, edition, table, source URL and SHA-256; loading fails on a missing file or a checksum mismatch. Tests that need the tables skip unless both the reference data and the standards directory exist.

## Roadmap, in order of colorist value

1. **Output transforms.** Explicit display encodings: Rec.709 BT.1886 2.4, sRGB, P3-D65 2.6, and HDR Rec.2100 PQ/HLG rendered from the film state before the SDR clip (re-expanding an already-clipped print shoulder doesn't work).
2. **Video.** AVAssetReader / AVPlayerItemVideoOutput pixel buffers enter as raw code values (no color matching) → input transform → Renderer → AVAssetWriter (HEVC 10-bit, ProRes 422). Add gate weave and flicker as optional temporal texture.
3. **LUT export.** Bake input transform → film system → output transform into 33³/65³ `.cube` LUTs for Resolve/Baselight/Premiere. Spatial effects (grain, halation, local tone) can't be LUTs and are listed as excluded.
4. **Stocks from public data.** Fit the negative and print model parameters to Kodak's published datasheet curves (Vision3 250D/500T characteristic and spectral-sensitivity curves; 2383 print), with a fitting report. Add lab controls: push/pull, printer-light points, print density, bleach-bypass (silver retention).
5. **Colorist tools.** True RAW white balance (kelvin/tint in camera space via `CIRAWFilter`) is done in the engine and `RenderService` (MOV-10); the editor control is pending, ideally on a kept-alive filter (see [RAW white balance](#raw-white-balance)). RAW decoder 9 is not used (see [RAW white balance](#raw-white-balance)). Next: acutance (edge contrast) and aura; scopes (waveform, parade, vectorscope) driven from the same render.
6. **UI.** SwiftUI with iOS 26 Liquid Glass. Simple by default: one look, Light / Color / Texture. Depth on demand. Native iPhone Duo layouts once Xcode 27.1 is installed.

## What we deliberately don't do

- No copying of another product's looks, data, code or branding. Chromagraph and Filmbox are references for *what* colorists value, not sources.
- No claims of matching any specific film or product without a measured comparison.
